# Test support for the Usher Controller

The shared scaffold every controller test stands on. It holds no tests of the controller itself;
those arrive per ticket. Run everything from `apps/controller`, with Docker running:

    pnpm test            # every test, against PostgreSQL 15 (the floor) and Valkey
    pnpm test:newest     # the same, against the newest PostgreSQL major released
    pnpm typecheck

From the repository's root, `pnpm test:controller` runs the same suites. The root's `pnpm test`
leaves them out, since they need Docker.

The Docker daemon can be this machine's or a remote one, named by `DOCKER_HOST`, with
`TESTCONTAINERS_HOST_OVERRIDE` naming the address its containers' ports are reached at. The
controller and every relay still run on this machine, on `127.0.0.1`. A remote daemon's host must
let this machine reach ports 30000 to 32767, where a test file's own container is published, and
the range the daemon assigns ports from; and a connection to one of those ports while nothing
listens there must be refused, not dropped, since an outage test waits for a stopped container's
port to refuse.

## The modules

- `controller.ts`: the seam, the only place a test reaches the controller. It states the contract
  the implementation must meet (`readConfiguration`, `createController`, `migrate`, `createAuditTrail`,
  `writeSeededPolicy`, and the process entry `src/main.ts`) as types, and loads the app's modules at
  run time. Until a module exists, every call through it fails with "the Usher Controller is not
  implemented yet: <module> is missing". `writeSeededPolicy` writes the policy a start seeds through
  the controller's own audit trail and store export, for `STARTED_STORE_TEMPLATE`. `environmentFor`
  is the one place the controller's environment variable names live, and `ENVIRONMENT_VARIABLES`
  exports them, so a test names a variable without spelling it; the clock and the log stream never
  have one. `spawnController` runs the process entry as a child given exactly one environment, for
  R1's one process-level test, or a built entry under Node alone, for the build's test beside
  `tsdown.config.ts`, and reports its exit, its output and whether it ever accepted a
  connection. `spawnSchemaMigrationCommand` runs the run's build of the schema migration command,
  `migrate.js`, the same way, sending it a signal on cue (`stopWith`) for a test of its stop, and
  `spawnWithUncaughtFailure` runs either built entry and, once the entry's own code has run, raises
  an error nothing catches in it, thrown or as a rejection nobody handles;
  `migrateThroughCommand` applies every migration through it, resolving with the lines it wrote to
  standard output and rejecting with what it wrote when it fails, and
  `schemaMigrationEnvironmentFor` expresses a run's options but a target as its environment, the
  URL's password in a variable of its own, the runtime role as the user of the controller's own
  `USHER_DATABASE_URL`, and the floor as a token lifetime with no grace period or margin. A run
  through a target goes through the seam's `migrate`, in-process, since the command applies every
  migration. `SCHEMA_MIGRATION_ENVIRONMENT_VARIABLES` names the command's own variables. For
  refusal tests, `readRefusal` and `startOutcome` give what reading a configuration or starting
  threw, the seam's own message thrown on rather than taken for a refusal; `refusalText` shows all a
  refusal carries; `changedVariables` names the variables two environments differ in; and
  `captureLog` records the lines written to a `logStream`.
- `containers.ts`: the only module that starts and stops containers, with the exact image tags. It
  also starts a PostgreSQL, with server settings when asked, or a Valkey of a test file's own, which
  pauses, unpauses, stops and restarts at one URL, for an outage test or one needing many
  connections, so neither reaches the run's shared containers, which every other file is using at
  the same time. Its URL holds a fixed port from 30000 to 32767, drawn again when the daemon reports
  one taken (`startOnFreeHostPort`, `reportsHostPortTaken`). `startRelay` puts a loopback relay, TCP
  or aware of HTTP paths, between a client and a server, to pass, refuse, freeze, reset, delay or
  pace what one client sees, on every path or on one of the bridge's (`RELAYED_PATHS`: `exchange`,
  `notices`, `notices/stream`), and switches its target between controller instances: an HTTP delay
  holds the answer's start, the request forwarded at once; a pace spaces an answer's chunks; a
  freeze holds a request or an answer until another mode lets it go on; a refusal leaves what is
  open as it was, a stream included, and `close` ends it too; an HTTP path can be answered a status;
  `cut()` resets what is open and refuses what comes. The latest mode set wins, a mode for every
  path replacing each path's own, and the relay stops listening only while every path refuses or
  closes. `openCacheConnection` speaks Valkey's protocol, each wait failing once the connection ends
  or its timeout passes; `flushValkey` empties a cache of a test's own, `suiteFlushedCache` gives a
  suite one Valkey flushed for each test asking, and `watchCache` reads every message published on
  one. `startKeycloak` starts a current Keycloak with a realm imported, reaching the host through
  Testcontainers' host access, for the tests whose outcome is Keycloak's own behaviour, and reached
  through a TCP relay on `127.0.0.1`, so its issuer is a loopback URL wherever the daemon runs;
  `addressKeycloakRealm` is the realm the address suites look people up in, its directory client
  given to the controller by `directoryFor`, its accounts disabled or deleted while a test runs, and
  an owner, an outsider and two accounts a test disables or deletes for the grants suites.
  `KeycloakRealm.subject` gives a person's subject by username.
- `containerEnvironment.ts`: how the containers' URLs travel to the test files, as environment
  variables, and `runningContainers()`, which a test calls to read them. Tests never import
  Testcontainers.
- `globalSetup.ts`: Node's test runner calls it once per run, under `--test-global-setup`, to start
  one PostgreSQL and one Valkey and build the controller, at once, and publish them. Node loads it
  without tsx, so it loads its three modules by their `.ts` names, and those three keep to syntax
  Node's type stripping accepts. If the flag changes, a wrapper script can start the containers,
  build the controller and set the same variables instead, with no test file touched.
- `build.ts`: builds the controller with its committed `tsdown.config.ts`, the output folder alone
  changed, into a `build-<uuid>.tmp/` folder inside the app, which the run's teardown removes; how
  the folder travels to the test files, as an environment variable; and `builtEntry()`, which a test
  calls for `main.js` or `migrate.js`, to run under Node alone.
- `database.ts`: `createTestDatabase()` gives a test file a database of its own, cloned from a
  template migrated once per run through the seam's `migrate`, with connections under the
  schema migration role (`usher_migration`, owning the schema) and the controller's runtime role
  (`usher_controller`). The superuser creates roles and databases and is never handed out. A
  template whose migration fails is dropped, and the failure is that file's alone. A
  retention floor other than the template's is set by running the migrations again on the clone, as
  a deployment does, and a database goes on a test file's own PostgreSQL by its superuser URL, or
  through `createDedicatedTestDatabase`, which starts that PostgreSQL and removes it at close.
  `readOnlyUrl` gives `READ_ONLY_ROLE`, `usher_read_only`, read access to a database's tables and its
  URL, creating the role on first use: no deployment creates it, and only the EGO migration's dry run
  test uses it.
  `blockedBackends` and `untilBlocked` see a statement wait on a lock by backend, a row's lock
  included, and `holdTable` and `untilWaiting` hold a table so a read of it waits; `whileHolding` runs
  work while one is held, and `writerIsWaiting` sees a transaction that wrote one table wait on
  another's lock. A connection lost while held, such as when a test stops its own PostgreSQL, fails
  the query made on it next rather than ending the test process.
- `policy.ts`: every table and column the tests name, and seeding by SQL (#209 Q1): `seedPolicy`
  writes a typed fixture in one transaction under the system actor (R9), invitations, a resource's
  own categories and a retirement included, and returns the internal ids it wrote by the fixture's
  names; it can run again on one database, finding a person and an application already held. A
  fixture names an application by a label, written as its display name, and seeds it under the id
  given, such as one registered through the API, or else under `fixtureApplicationId`'s uuid for the
  label, so seeding again finds it; `seeded.applications` gives each one's id by its label. Each
  person is written with their one identity, and a person already held is found again through
  `user_identities`. `declareActor` and `inTransactionAs` declare who acts, as the audit triggers
  read it. The changes a test makes by SQL (`liveGrantId`, `revokeGrantInStore`, the group and
  principal changes, `alterEncryptedKey`, which alters one stored application key, and
  `copyEncryptedKey`, which copies one onto another key's row) and the notice table's helpers
  (`insertNotices`, `noticesAfter`, trims, epochs,
  restores, and the holding and refusing triggers) live here too, as do `usersWithSubject`, and
  `trimNotices` and `trimNoticesOpen`, which call `trim_notices()`, and `trimNoticesBounded`,
  which calls `trim_notices(max_rows)`, with `BOUNDED_TRIM_REFUSAL`, its refusal's SQLSTATE;
  `RETENTION_SWEEP` holds the retention sweep's cadence, lock and bound, and `holdRetentionSweep`
  holds its lock in a test's session, so every run beginning meanwhile deletes nothing;
  `noticeSubject` says what
  `notices.idp_subject_id` holds. A fixture resource's
  `registeredAt` and `updatedAt` are set once the rest is seeded and read back into
  `seeded.resourceTimes`; `mergedPolicy` combines fixtures. `OWNER_ROLE` names the owner role and who
  counts as an owner; `addAcceptedOwner` writes an owner grant with its acceptance, and `retireInStore`
  retires a resource and ends its owner grants in one transaction. The store readers: `policySnapshot`,
  `storedExternalIds`, `resourceIdOf`, `userIdOf`, `internalIdsInStore`, `grantCountOn`,
  `isRetiredInStore`, `servedByInStore`, `changeRecordCount`, `storedCapabilities`, and
  `storedResourceTimes` with `setResourceTimesInStore`, and `keyEncryptionKeyChecks`, the
  key-encryption key's check values. Every reader naming a person by subject
  reads it through `user_identities`, and `storedGrants`, which reads one identity per person, fails
  saying so on a person holding two. `noticesAfter`'s `transaction` is the row's `xmin`, which
  cannot show that rows share a top-level transaction (its TSDoc says how to show that).
  `takeStoreSnapshot` reads every table of the schema and every sequence's state in one consistent
  read, as a backup does, and `restoreStoreSnapshot` puts them back as a restore does, the schema's
  user triggers disabled while it runs; `tablesOf` and `rowsIn` read a snapshot.
  `DECISION_ORIGIN_COLUMN` names the decision row's mark of a migrated acceptance. `SEEDED_ROLES` is
  permissions-model.md's seeded matrix, every role's capabilities and plane, the one source for what a
  person answering a grant is shown; `STARTED_STORE_TEMPLATE` is the controller's template with the
  policy a start seeds written by the controller's own code, through the seam's `writeSeededPolicy`
  under `STARTED_STORE_SETTINGS` (the harness's default rules, event source and instance): the
  vocabulary, the seeded roles, and the rules digest with the first start's `baseline.change` row,
  all a started store holds but the key-encryption key's check value, for a test seeding a fixture
  that names those roles while starting no controller. `storedGrants` reads the store's grants by
  holder, id, resource and role, and `rowCountOf` and `rowCounts` (with `GRANT_WRITTEN_TABLES`)
  count rows. `failNthInsert` fails the Nth insert into a table of a test's own database, through a
  test-only trigger it creates and drops.
- `identityProvider.ts`: an OpenID Connect stand-in for a Keycloak realm on loopback: discovery, a
  JWKS, Keycloak-shaped access tokens, key rotation, and each failure mode a test can ask for. A
  second realm on the same host and port, from `addRealm`, signs with keys of its own, its tokens
  always naming it as their issuer. A discovery document can name the issuer with a trailing slash,
  or `otherIssuer`, `/realms/not-<realm>`, a realm the stand-in never serves.
  `mintServiceAccountToken` mints `SERVICE_ACCOUNT`'s client-credentials token, signed as every token
  is.
- `bridgeWire.ts`: the bridge's side of the wire, reproduced from its source because those functions
  are internal to the bridge: subkeys and the subject tag, the channel assertion signer, the token
  reader, the channel reader and the push's stream reading. Each export names the bridge file and
  function it follows; when the bridge changes one, change the copy to match. It also gives a
  subkey's bytes, the assertion's `typ` and lifetime, and a JWE's plaintext as the channel reader
  decrypts it. `isUsableResource` reproduces usher-types' internal rule for a value naming a resource.
- `exchange.ts`: `POST /exchange` sent exactly as the bridge's controller client sends it, with the
  departures a malformed-request test needs, and `readUsherToken`, which reads the answer through
  `bridgeWire.ts`. Also `PEOPLE`, the one cast of synthetic people every ticket names, hostile
  subjects included (a quote and a backslash, markup, SQL's wildcards and a subject they would match),
  their sign-in tokens, and `readUnderKey`, which reads a token under a key of the test's choosing.
  `carriesToken` finds an Usher token in an answer's body, and `comparableWireRefusal`, with
  `PER_ANSWER_HEADERS`, is the one comparison of two refusals that must be identical on the wire, at the
  exchange and at the channel alike.
- `channel.ts`: `GET /notices` and `GET /notices/stream` sent exactly as the bridge's poll and push
  send them, each answer read through `bridgeWire.ts`; `pollAll` pages from a cursor to the newest
  notice, and the stream client yields each event with its arrival time and its bytes, or waits at
  most a given time for one with `nextWithin`. `openRawStream` reads the stream at the socket, for a
  test that times bytes or stops reading.
- `admin.ts`: one function per Policy Management API operation, and the back-channel logout
  endpoint, with every path, body and header they use, and the management and logout tokens the
  stand-in mints for them. A grant's creation answers with its id read, and `assertSucceeded`
  names the status and code of an answer that did not succeed. `readReadiness` and `readLiveness`
  ask the unauthenticated health endpoints. The application operations (`registerApplication`,
  `issueApplicationKey`, `revokeApplicationKey` and `readApplication`) follow the controller's
  OpenAPI document: `registeredApplicationOf` and `issuedApplicationKeyOf` read the only answers
  holding a key's value, `applicationViewOf`, `readApplicationView` and `revokedApplicationKeyOf`
  read answers holding none, with `APPLICATION_KEY_MEMBERS`, and `cacheDirectivesOf` reads an
  answer's `Cache-Control`; `APPLICATION_DISPLAY_NAME_MAXIMUM_LENGTH` and
  `APPLICATION_LIVE_KEY_LIMIT` hold their limits. Beside the operations: `PROBLEMS`, every problem
  code with its status, and the reason vocabularies (`APPLICATION_KEY_REVOCATION_REASONS`,
  `GRANT_REVOCATION_REASONS`, `SYSTEM_ASSIGNED_REASONS`,
  `RESOURCE_REVOCATION_REASONS`, `PLATFORM_REVOCATION_REASONS`, `IDENTITY_REVOCATION_REASONS`,
  `SUPPRESSION_REASONS`, `RESTORATION_REASONS`) and `deniedEventReason`, the reason a denied event
  records; the answers' shapes, with `LISTING_QUERY`, `INCLUDING_REVOKED`, `INCLUDING_RETIRED` and
  `GRANT_STATES`, and their readers: `mediaTypeOf`, `bodyObjectOf`, `resourceView`, `resourceViewOf`,
  `readResourceView`, `grantView`, `listedResources`, `listedResource`, `listedExternalIds`,
  `listedGrants`, `nextCursor`, `pageMembersBeside`, `resourcePages`, `holderOf`, `rolesHeld`,
  `carriesGrantSummary`, `categoriesOf`, `resourceFieldsOf` and `auditPageOf`; one refusal
  comparison, `comparableRefusal`, and `comparableSuccess` with `shapeOf` for two answers that must be
  indistinguishable; C2's assertions, one per status (`assertUnreadable`, `assertCredentialRefused`,
  `assertForbidden`, `assertNotFound`, `assertConflict`, `assertUnsupportedMediaType`,
  `assertRuleBroken`, `assertUnavailable`) on `assertRefused`, and `assertProblemSays` for a refusal's
  text; `sendRaw`, which replays an operation at the socket with several `authorization` lines or no
  `content-type`; `FIELD_CATEGORY_MEMBER`; `INTERNAL_DETAIL` and `internalDetailIn`, one check for
  internal detail and internal ids; and `stringsIn`, `instantOf`, `administratorCaller` and
  `personCaller`. Suppressing and restoring take an optional `reason` beside their departures.
  `sendSlowly` sends an operation's headers at once and a large body slowly, and tells whether the
  answer came before the body ended; `BODY_LIMIT_BYTES` holds each endpoint's body limit, and
  `namesBodyLimit` finds it in a `bodyTooLarge` refusal's detail. `EXTERNAL_ID_MAXIMUM_LENGTH` is the
  longest externalId #211 Q3 allows, beside the registration helpers. `MANAGEMENT_ROUTES` holds every
  Management API operation as the contract's routes name it, `managementRouteOf` matches a request's
  method and path to one, and `managementRouteOfOperation` reads the route an operation reaches from
  the request it sends to a recording server.
- `auditEvents.ts`: `readAuditEvents` reads `audit-events.md`'s Events table as the bridge's own test
  does, extended with field sets split by result, a severity following `result`, the Actor column's
  roles and whose each row is. A field set also holds the names before a `when` or `for` in one of
  a clause's comma-divided items, carried only under the condition that word opens, as
  `grant.revocation`'s `causedBy` when a retirement ended it, and a clause pointing below the table
  takes the names the event's note there lists, as
  `migration.run`'s counts; a severity may name one case per clause, `when refused`, `for` a value the
  fields cell lists and `else`, as `applicationKey.revocation`'s does. Every controller row whose
  actor is a principal follows the note's rule for a refused request: refused, its event carries
  `reason` and records at `warning`. `fieldSetsIn` and `severityIn` read one cell each.
  `AUDIT_EVENT_TYPES` names every event the tests use, each a row of the table; `cloudEventsIn` reads
  a log stream's lines, such as `captureLog`'s, as CloudEvents, refusing a line that is not one JSON
  object holding each member once. The line's `SEVERITY_ATTRIBUTE` and `LOG_LEVEL_MEMBER`, the rows
  nothing in this epic emits in `NOT_EMITTED_IN_THIS_EPIC`, `EVENT_INSTANT_FORM`, `CAUSED_BY_MEMBER`
  for a retirement's revocations and a migration's writes, `MIGRATION_ORIGIN` and
  `MIGRATION_ORIGIN_EVENT_TYPES` for the EGO migration's writes, `MIGRATION_RUN_COUNTS` for its run's
  event and its dry run's line (`DRY_RUN_LOG_LINE`, `dryRunLogLines`), `TOKEN_CAP_EVENT` for an
  exchange past the bridge's response cap, and the event-only vocabularies
  `EXCHANGE_REFUSAL_REASONS`, `CHANNEL_ASSERTION_REJECTION_REASONS` and `FAULT_REASONS` live here
  too, with a refused management credential's reasons (`MANAGEMENT_TOKEN_REFUSAL_REASONS`,
  `MANAGEMENT_TOKEN_TALLY_REASONS`), its tally interval (`REFUSAL_TALLY_INTERVAL_MILLISECONDS`,
  `TALLY_WITHIN_MS`) and its readers (`managementTokenRefusal`, `managementTokenRefusalsIn`,
  `refusalTalliesIn`, `credentialRefusalsElsewhere`), and `REFUSED_SUBJECT_MEMBER`, the member naming
  a verified but refused token's subject. The event readers are here as well: `eventsIn`, `ofType`,
  `dataOf`, `eventDataOf`, `awaitEvents`, `awaitEventsOfType` and `awaitEventData` over a captured
  log stream, and `auditRows` and `auditRowTexts` over the `audit_log` table.
- `harness.ts`: `startHarness()` stands up a test file's database, the stand-in, a configuration
  with a fresh cursor key and key-encryption key, the controller, its applications and a seeded
  fixture, and stops them all with one `stop()`. The configuration names no application, since the
  database is the only list of them, and holds each store's password apart from its URL
  (`passwordsApart`), as in a deployment. Once its own controller first listens, the harness
  registers its applications through `POST /admin/applications` as the platform administrator, by
  display name (`arranger-test` and `lyric-test` by default, none for an empty list, then each
  further one named by the fixture, `harnessApplicationNames`), and `application(displayName)` gives
  each one's id and first key. The fixture is seeded by SQL once the controller has started, since
  it writes the seeded roles at its start (#207 Q11), each of its applications under its registered
  id (`withRegisteredIds`), so seeding writes only what each serves; nothing is seeded before the
  start. With `startsController: false` the fixture is seeded whole first, its applications under
  the fixture's ids, and each is issued its first key once the harness's controller first listens.
  The platform administrator registering them and issuing their first keys holds the token
  `administratorToken` gives: by default `standInAdministrator`'s, minted by the stand-in, and for a
  controller trusting a Keycloak realm `realmAdministrator`'s, the realm's own administrator signed
  in through its management client, so each application's registrant is a principal the controller
  trusts, as in production. A harness started before its realm takes `realmRegistrar`'s source and
  gives it the realm with `started` once the realm is up, before the harness first listens. The
  database's retention floor is the configuration's;
  an outage test passes its own
  PostgreSQL as `postgresql`, or its own stand-in as `identityProvider`; `restart` starts the
  controller again with new settings, and `startsController: false` leaves the starting to a test
  running its own instances. `withHarness` gives a test a harness of its own, stopped once the work
  settles or, given the test's context, as a step of its cleanup deferred at the start, so whatever a
  test starts on it later stops first; `suiteHarness` one
  harness a suite's tests share, and `configurationToRead` a configuration for a test that only reads
  or refuses one. `startInstance` starts a second controller beside the harness's, on its store,
  cache and keys, under an instance name of its own, and `startReadOnlyInstance` one on the read-only
  role. `stopController` and `startController` stop and start the harness's controller apart, a new
  start listening on the port the last one did, so a bridge pointed at it reaches the restarted
  controller; `restart` is the two in turn. `takeSnapshot` and `restoreSnapshot` take a snapshot of a
  running harness's store and restore it as the runbook does: the controller stopped, the snapshot
  restored, a new `notice_stream.epoch` unless the test keeps the snapshot's, the controller started
  (#215 Q12, #217 Q3). `COMPRESSED_CONTROLLER_TIMING` is the controller's half of #217's compressed
  profile, `RETENTION_DEFAULTS` the production token lifetime, grace period and margin, and
  `APPLICATION_KEY_RELOAD_INTERVAL_MILLISECONDS` the controller's 30 s reload of the live
  application keys. Each
  database connection the harness holds fails the query made on it next once its PostgreSQL goes,
  rather than ending the test process.
- `vendoredBridge.ts`: the bridge run as a host runs it, for #215's expectations and
  scenarios and for #217. `startBridge` creates the core with `createBridgeCore`, registers its keys,
  mounts its Express middleware in a loopback app answering each request it lets through with the

  key, the controller's issuer and a timing profile. `TIMING_PROFILES` holds #217's two, `compressed`
  and `ims`, each a bridge half and a controller half, and `resolvedBridgeTiming` a profile's values
  with the bridge's defaults filled in. `createRecordingFetch` is the fetch the bridge is handed: it
  runs on undici with an Agent of its own, as the bridge's own fetch does, taking undici from the
  bridge's dependencies rather than this project's, and records each request's start, method,
  path, query, `Last-Event-ID` and body, cut at `RECORDED_BODY_CHARACTERS`, each answer's status and
  arrival, a poll's `next` and `more` read from a copy of its answer under the application's key, and
  a request that failed; `exchangedCredentialOf` reads an exchange's credential from its body.
  `createRecordingLogger` records each event the bridge logs with its arrival, and waits for one with
  `nextEvent`. `startBridge` takes a timing override over its profile, and a started bridge gives its
  resolved `timing`. `blockGlobalDispatcher` blocks the process's global dispatcher on the bridge's
  own undici, as a host might. The observers read what a bridge recorded: `requestsTo`, `isHeadPoll`,
  `afterCursorOf`, `eventsSince`, `modeChangesSince`, `nextModeChange`, `nextNotice`,
  `entriesDropped`, `untilMode`, `settledPollStart` (the start of the first check from now, waited
  through every page it asks for), `principalOf` and `reaches`, with `INTERVAL_JITTER` and
  `SCHEDULING_SLACK_MS`.
- `express.d.ts`: types for Express, which ships none, so `vendoredBridge.ts` can mount the
  middleware; it follows the bridge's own `testExpress.d.ts`.
- `conformanceCorpus.ts`: what #215 needs of the conformance corpus. `CORPUS_CASES` is the static
  list a test file registers from (the cases replayed with the configuration each runs under, and the
  unreachable and omitted ones with their reasons), and `EXPECTATION_CASES` the expectations' four.
  `readCorpusEntry`, `readCorpusExpectation` and `readCorpusIndex` are the one place #215 reads the
  corpus, `.dev/design/conformance/` at the repository's root, and only inside a test body; while the
  corpus is missing or in its old form, each fails naming the corpus and saying the suites read its
  corrected form, so no payload's difference from an old corpus can be read as the controller's. `assertConformsToCorpus` and
  `comparablePayload` are #215's payload comparison, which reads the corpus's `aud`, `arranger-prod`,
  as an application's label, comparing the id the harness registered that application under;
  `CONFORMANCE_CONFIGURATIONS` holds A, A-off,
  A-auto, A', B and B-off as harness options; `CORPUS_ANA` is the corpus's principal.
- `sqonEvaluator.ts`: usher-types' test-only SQON evaluator (B3), copied from `modules/types` with the
  plain-data helpers it uses, each export naming the file and function it follows, and its own tests
  copied beside it.
- `directory.ts`: `startDirectory`, a stand-in for the identity provider's directory lighter than a
  Keycloak, answering the admin API's lookups of accounts by address and by id behind a client
  credentials token, set per test to hold one account, none, a disabled one, or two holding one
  address, and to fail from a numbered lookup on or every lookup by id (`failLookupsById`); each
  account carries a given and a family name, whichever way it is looked up
  (`directoryNamesOf`), so a scan can show no name is ever stored. The two #216 tests whose outcome is
  Keycloak's own use the real realm.
- `recordingServer.ts`: a loopback server recording every request and answering as a test scripts
  it, for the support modules' own tests and any stand-in a ticket needs.
- `waiting.ts`: `eventually`, `nowSeconds`, `settledWithin`, and the cleanup registries `cleanupFor`
  (one test, the same registry for every call in it) and `suiteCleanup` (one suite), each step run
  last first.
- `clocks.ts`: the clocks a test configures the controller with, `fixedClock` and `adjustableClock`;
  `KEY_REFETCH_COOLDOWN_MS` (#208 Q5); and the waits until an instant of either of the process's own
  clocks, `untilMonotonicTime` (`performance.now()`, as the bridge's recordings are timed) and
  `untilWallTime` (`Date.now()`, as tokens and rows are dated), named apart.

`pnpm test` finds tests the way Node's runner does: every `*.test.ts`, every file named `test-*`, and
every file anywhere under a directory named `test`. A helper module belongs here in `test-support/`,
under any other name, or it runs as a test file.

## The seam rule, at every boundary

Tests reach the controller only through `controller.ts`. The same holds at every other boundary:
each path, body member, header, table, column, setting and mechanism a test assumes lives in
exactly one support module, so the implementation aligns with the tests by one edit there, and a
reviewer reads every assumption in one place. A ticket test names an operation, a table or a column
through its module, never as a literal of its own.

Where a design document or a ruling fixes a name, the module uses it. Where nothing fixes it, the
module proposes one, listed below. This table is what Usher reviews to see what the tests pin beyond
the decided design.

## The copies

Some of this support copies or reproduces what the bridge and usher-types keep internal:

- the reproductions in `bridgeWire.ts`, since the bridge does not export those functions;
- `sqonEvaluator.ts`, a copy of usher-types' evaluator, which the package keeps off its root.

`vendoredBridge.ts` takes undici from the bridge's own dependencies, the copy the bridge's default
fetch runs on.

## The images

PostgreSQL runs at the floor, the oldest major the deployments run (15), by default, and at the
newest major released under `pnpm test:newest`. Valkey runs at one exact tag. Each is an exact
minor tag from Docker Hub, set in `containers.ts`; move a tag by editing it there.
