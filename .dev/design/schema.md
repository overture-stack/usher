# The database schema

_The controller's PostgreSQL store, physically: tables, columns, keys, the indexes the token
calculation needs, and the decisions the logical model left to this document._

**Status: a draft for review.** It turns the logical model in
[permissions-model.md](permissions-model.md) § Entity schema into tables, reads each against the five
steps of [token-calculation.md](token-calculation.md), and adds the channel half that
[bridge-tests.md](../docs/bridge-tests.md) fixes for the controller. Eight decisions are marked
**Decide** below, each with a recommendation. Nothing here is built yet.

---

## What is stored where

| Store                    | Holds                                                                                           | Why there                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| PostgreSQL               | the policy model, the notice stream, and the audit log                                          | the source of truth: transactional, and read by every controller instance            |
| Valkey                   | the payload cache behind the refresh fast path, and the pub/sub waking instances to new notices | shared between instances, and disposable: losing it costs recomputation, never truth |
| Controller configuration | the capability vocabulary's defaults, token lifetime, grace period, poll interval               | changes with a release or a deployment, never at runtime                             |
| Instance configuration   | the baseline and the signed-in rule, and the platform's default base tier                       | settings of the instance rather than facts about any principal                       |

Nothing a principal is granted lives outside PostgreSQL, so a Valkey loss never widens access: the
fast path finds no cached payload and recomputes from the store.

---

## Conventions

- **Identifiers** are `uuid`, generated by the database with `gen_random_uuid()`. Grant identifiers
  travel in audit events and through the management API, so they are opaque and unguessable rather
  than sequential. The one exception is the notice stream's position, which must be ordered.
- **Times** are `timestamptz`, written and read in UTC, never a date: selecting the latest decision
  needs a total ordering, and two answers can land in the same minute.
- **Fixed vocabularies** are `text` with a `CHECK` constraint rather than a PostgreSQL enum, since
  adding a value is then a constraint change rather than a type migration.
- **Foreign keys** are `ON DELETE RESTRICT` throughout. Nothing a grant points at is deleted while
  the grant exists, and grants are never deleted, only revoked or expired.
- **Append-only tables are append-only by privilege**, not only by convention: the controller's
  database role holds `INSERT` and `SELECT` alone on `grant_decisions`, `notices` and `audit_log`,
  and on `principal_revocations` may update only `lifted_by` and `lifted_at`. A defect in the
  controller then cannot rewrite history, which is the property the audit trail rests on.

---

## The tables

Read in the order of the token calculation's steps, which is the order each table is needed.

### Principals

    users
      id                 uuid         primary key
      idp_issuer         text         not null
      idp_subject        text         not null
      created_at         timestamptz  not null
      unique (idp_issuer, idp_subject)

`users.id` never leaves Usher; outside it a principal is the provider's subject, unique only together
with its issuer. A row is written at a principal's first exchange, and no email address or display
name is stored.

    principal_revocations
      id                 uuid         primary key
      user_id            uuid         not null  references users
      revoked_by         uuid         not null  references users
      revoked_at         timestamptz  not null
      reason             text         not null
      lifted_by          uuid                   references users
      lifted_at          timestamptz
      check ((lifted_by is null) = (lifted_at is null))
      unique (user_id) where lifted_at is null

**Decide A: revoking a principal entirely is a history table of its own.** Recommended over the two
alternatives the corpus left open:

| Option                                      | Why not, or why                                                                                                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `revoked_at` on each of the person's grants | a grant conferred by a rule has no row, so the signed-in rule would keep reaching a revoked person; case 33 needs a fact about the principal, refused at the exchange |
| `revoked_at` on `users`                     | says it directly, but lifting it erases when and why it was set, and the trail needs both                                                                             |
| **`principal_revocations` (recommended)**   | the current state is the row with no `lifted_at`; history survives a lift, and the exchange reads one indexed row                                                     |

The fast-path rejection of a per-principal marker does not reach this: that marker existed to detect
changes to what a principal holds, where this one records that the principal is stopped altogether.

### Groups and membership

    groups
      id                 uuid         primary key
      resource_id        uuid         not null  references resources
      name               text         not null
      description        text
      created_by         uuid         not null  references users
      created_at         timestamptz  not null
      unique (resource_id, name)
      unique (id, resource_id)

    group_users
      group_id           uuid         not null  references groups
      user_id            uuid         not null  references users
      primary key (group_id, user_id)

**Decide B: a group belongs to one resource.** [token-calculation.md](token-calculation.md) already
reads the question as a threat, a group landing grants across resources from one membership change
no resource's owner sees, and answers no; what remained open was only how to express it. A
`resource_id` on the group, and the composite key below on grants, make a group grant on another
resource impossible to write. Groups carry no rows in the first release, so this costs nothing now.

### Resources and categories

    resources
      id                 uuid         primary key
      name               text         not null  unique
      description        text
      base_tier          text         not null  check (base_tier in ('open', 'registered', 'grant'))
      suppressed         boolean      not null  default false
      registered_by      uuid         not null  references users
      registered_at      timestamptz  not null
      updated_at         timestamptz  not null

`name` is the identifier the data carries and the payload names, so it is unique; what happens when a
registration collides with an existing one is the roadmap's "Resource identifier collision at
creation". Registration accepts a name only from an allowed set of characters, by default letters,
digits, dot, underscore and hyphen, which an instance can widen in configuration. It also refuses a
name holding a marker that a search application reads as an instruction in a filter value, `*`,
`__missing__` or `set_id:`, using the list `usher-types` exports, since `__missing__` is made only of
allowed characters, and a name differing from an existing one only in letter case. The bridge lists
resource names in its filters and refuses any such value, so every narrowing naming that resource
would otherwise fail.

    categories
      id                 uuid         primary key
      scope              text         not null  check (scope in ('global', 'resource'))
      resource_id        uuid                   references resources
      name               text         not null
      description        text
      check ((scope = 'resource') = (resource_id is not null))
      unique nulls not distinct (scope, resource_id, name)

    resource_categories
      resource_id        uuid         not null  references resources
      category_id        uuid         not null  references categories
      primary key (resource_id, category_id)

The uniqueness treats a null `resource_id` as equal to another, so two global categories cannot share
a name; PostgreSQL otherwise counts nulls as distinct. `unmarked` is a seeded global category. A payload names a category with its scope, `global.unmarked`,
which is `scope` and `name` joined. That every live resource offers at least one category is enforced
by the controller when a resource is registered, since a constraint across two tables at commit would
cost a deferred trigger for a rule the registration path already holds.

### Applications

    applications
      id                 text         primary key
      description        text
      registered_by      uuid         not null  references users
      registered_at      timestamptz  not null

    application_resources
      application_id     text         not null  references applications
      resource_id        uuid         not null  references resources
      primary key (application_id, resource_id)

`applications.id` is the audience, as `aud` names it. Its key lives in the secrets store and never in
the database. `application_resources` is what case 18 in
[token-calculation.md](token-calculation.md) reads: a grant on a resource the audience does not serve
is left out of that audience's token. A resource can be served by several applications. Who may write
the mapping is open, with resource registration in [admin-model.md](admin-model.md).

### Capabilities, roles and permissions

    capabilities
      id                 uuid         primary key
      entity             text         not null
      action             text         not null
      display_name       text         not null
      description        text
      unique (entity, action)

    roles
      id                 uuid         primary key
      name               text         not null  unique
      plane              text         not null  check (plane in ('data', 'control'))
      description        text

    role_permissions
      role_id            uuid         not null  references roles
      capability_id      uuid         not null  references capabilities
      primary key (role_id, capability_id)

The capability vocabulary's defaults come from controller configuration and are seeded at startup;
an instance's additions are rows. Roles and their permissions are seeded from the matrix in
[permissions-model.md](permissions-model.md) § The seeded roles.

### Grants and decisions

    grants
      id                 uuid         primary key
      resource_id        uuid         not null  references resources
      record_category_id uuid                   references categories
      field_category_id  uuid                   references categories
      holder_user_id     uuid                   references users
      holder_group_id    uuid
      role_id            uuid         not null  references roles
      granted_by         uuid         not null  references users
      granted_at         timestamptz  not null
      expires_at         timestamptz
      revoked_at         timestamptz
      revoked_by         uuid                   references users
      check (num_nonnulls(holder_user_id, holder_group_id) = 1)
      check ((revoked_at is null) = (revoked_by is null))
      check (field_category_id is null or record_category_id is not null)
      foreign key (holder_group_id, resource_id) references groups (id, resource_id)

**Decide C: the holder is two columns rather than a type and an id.** The logical model's
`holder_type` and `holder_id` fail closed either way, as it argues, but a polymorphic id cannot carry
a foreign key. Two columns, exactly one set, gain referential integrity and are what lets the
composite key above confine a group grant to its group's resource. Enabling groups still adds rows,
not columns.

**Decide D: a null `record_category_id` is the control-plane wildcard.** An owner's grant reads
`(HEART_STUDY, *, user, Ana, owner)`; storing `*` as a null keeps the foreign key on every real
category. The controller refuses a null on a data-plane role and a field category on a grant whose
role carries `record.delete` (case 25) when the grant is written, since both rules cross into
`roles` and `role_permissions`, which a `CHECK` cannot reach.

    grant_decisions
      id                 uuid         primary key
      user_id            uuid         not null  references users
      grant_id           uuid         not null  references grants
      decision           text         not null  check (decision in ('accepted', 'rejected'))
      capabilities       text[]       not null
      decided_at         timestamptz  not null

`capabilities` is the snapshot of what the person was shown, as `entity.action` names, never a cache
of what the role confers now. Pending is the absence of a row.

### Invitations

    invitations
      id                 uuid         primary key
      email              text         not null
      resource_id        uuid         not null  references resources
      record_category_id uuid                   references categories
      field_category_id  uuid                   references categories
      role_id            uuid         not null  references roles
      link_token_hash    bytea        not null  unique
      invited_by         uuid         not null  references users
      invited_at         timestamptz  not null
      expires_at         timestamptz  not null

The link binds the grant to whichever verified account confirms it, so only a hash of its token is
stored: a leaked table cannot be replayed into grants. `email` is stored lower-cased, since a lookup
by address must match however the recipient typed it. The row is deleted once its grants are
written.

### The notice stream

    notices
      position           bigint       generated always as identity  primary key
      kind               text         not null  check (kind in ('principal', 'category',
                                                'baseline', 'global'))
      subject            text
      resource_name      text
      created_at         timestamptz  not null
      check ((kind = 'principal') = (subject is not null))
      check ((kind = 'category') = (resource_name is not null))

One table carries every kind the bridge's notice stream does. A principal's revocation and a sign-out
relayed from the identity provider are both `principal` notices naming the subject, since a bridge
treats them alike. A category change names the resource as the payload names it, and the baseline
and global kinds name nothing.

**Positions follow commit order, by serializing the writes.** An identity value is assigned at
insert, so two transactions can commit out of order and a poll reading between them would skip the
earlier one for good. Every notice write takes one transaction-scoped advisory lock before inserting,
so positions are assigned and committed in the same order. Notices are rare enough that the
serialization costs nothing measurable.

**A poll answers from a cursor, and a cursor history no longer reaches answers `410`.** A cursor is
opaque to the bridge and carries a position and an epoch. Notices are kept for the longest a bridge
may lag and still act on them: the token lifetime plus the grace period, with a margin. Trimming
records how far it reached, so the answer is judged against that watermark rather than against the
oldest notice left, and the epoch changes whenever history restarts, as after a restore, so restored
positions are never read as the old ones. A `410` drops every cached entry, which fails closed: the
bridge exchanges again for everyone, and nothing revoked survives. How a restore changes the epoch is
a step for the deployment runbook.

    notice_stream
      singleton          boolean      primary key  default true  check (singleton)
      epoch              uuid         not null
      trimmed_through    bigint       not null

**Decide E: category notices are filtered by audience, and principal notices are tagged per
audience.** The controller holds which applications serve which resources, since a token names only
those, so filtering a category change costs a join the token calculation already makes, and an
application never learns of changes to resources it does not serve. A principal notice cannot be
filtered: nothing records which applications hold a token for whom, and a stale record would withhold
a revocation silently. It goes to every audience, naming the subject by a tag, an HMAC of the subject
under a key derived for that audience, which a bridge computes for the subjects it holds. An
application then recognizes only the people it already serves. Baseline and global notices go to
every audience. Positions stay one sequence, and the cursors a bridge sees are opaque, so the gaps a
filter leaves say nothing about other applications.

| Option                                                      | What an application learns                                                           | What it costs                                                                               |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| unfiltered, subject in clear                                | every revocation and sign-out on the platform, and every resource's category changes | nothing                                                                                     |
| unfiltered, subject tagged                                  | every resource's category changes, and no person it does not serve                   | an HMAC for each audience on each principal notice                                          |
| **category notices filtered, subject tagged (recommended)** | changes to its own resources, and no person it does not serve                        | the HMAC, and a join already made for the token                                             |
| every kind filtered                                         | the same                                                                             | a record of which applications hold tokens for whom, whose staleness withholds a revocation |

The tag, the notice encryption and the bridge's side of the stream are set out in the bridge's
[revocation notice stream](../docs/atlas/bridge/revocation-notice-stream.md) research.

### The audit log

    audit_log
      id                 uuid         primary key
      specversion        text         not null
      source             text         not null
      type               text         not null
      occurred_at        timestamptz  not null
      dataschema         text
      data               jsonb        not null

The envelope is CloudEvents', as [audit-events.md](audit-events.md) sets out, with `occurred_at`
holding its `time` attribute, since `time` is a type name in SQL. `data` holds each type's payload. A grant conferred by a rule has no row, so the exchange records which rules applied
as an audit event, or the trail could not say who could reach what, and when. How long entries are
kept against a person's request for erasure is open in [to-discuss.md](to-discuss.md), and is not
decided here.

## The token calculation, against the indexes

| Step     | Reads                                                       | Index                                                                                                                             |
| -------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| exchange | is the principal revoked                                    | the partial unique index on `principal_revocations (user_id) where lifted_at is null`                                             |
| 1        | grants held directly, and through each group the user is in | `grants (holder_user_id) where revoked_at is null`; `group_users (user_id)`; `grants (holder_group_id) where revoked_at is null`  |
| 2, 4     | each kept grant's role, expanded                            | the primary key of `role_permissions`, read once per distinct role                                                                |
| 3        | this principal's latest decision on each grant              | `grant_decisions (user_id, grant_id, decided_at desc)`                                                                            |
| 4        | whether the resource still offers the category              | the primary key of `resource_categories`                                                                                          |
| 5        | which resources this audience serves                        | the primary key of `application_resources`; the payload, `resourceCategories` included, names only those, and is stored in Valkey |

Expiry is read at issuance, as `expires_at > now()`, rather than indexed: a principal holds few
grants, and an index on a moving comparison does not help. The controller caps an Usher token's `exp`
at the earliest of the kept grants' `expires_at` and the sign-in token's own `exp`.

## The data access layer

**Decide F: Kysely, a typed query builder, over an ORM or raw SQL.** The threat model requires
parameterized statements or a layer that binds parameters, and that constrains the choice without
making it.

| Option                             | Better                                                                               | Worse                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **Kysely (recommended)**           | SQL in typed TypeScript, always parameterized, no hidden queries, its own migrations | the schema's types are declared or generated rather than inferred from a model            |
| Drizzle                            | a schema written as code, with migrations generated from it                          | more abstraction between the query and what runs, on the path that decides access         |
| A raw driver with tagged templates | the fewest layers, and the plainest SQL                                              | parameterization depends on every call site using the template, which a review must catch |

The access-deciding queries are few and must read as plainly as the calculation they implement, so a
builder that emits exactly the SQL written suits them better than a model that decides it. The
management interface's queries, a custodian seeing only the grants they govern, are the same
residual-filter problem the bridge solves, and may want the same machinery later. Versions are
checked when the controller is built, not recorded here.

**Decide G: migrations are numbered, forward-only and reviewed.** Each runs in a transaction, none is
edited once released, and a correction is a new migration. Rolling back a deployment does not roll
back its schema, so a migration that removes anything ships one release after the code stops reading
it.

**Decide H: the controller's database role cannot alter the schema.** Migrations run under a separate
role at deployment, and the running controller holds only the privileges its queries need, the
append-only tables above included. A compromised controller can then read and write policy, which it
must, but cannot widen its own privileges or drop the audit log.
