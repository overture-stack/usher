## The permissions model implements half of a named pattern

The role and attribute hybrid is RABAC, which evaluates access in two stages: a role check for
whether a permission is held, then attribute filtering for which objects it reaches. The category
machinery is a well-developed second stage. The first stage, the assignment of permissions to roles,
was never defined, so the token carries a `role` label with no permission set behind it and the
model contains no verbs at all.

This resolves several items previously tracked separately as one: the create/read/update/delete gap,
the single `role` string against documented union-of-roles semantics, and the `public` synthetic role
that exists as a permission set described in prose. Correction recorded: resolve roles to permissions
at issuance and carry the permission set, since deciding what a role permits is a policy decision and
a plugin holding that table would hold policy.

One asymmetry recorded because it is the single place the pattern diverges from categories: the
permission vocabulary must be platform-fixed, because both controller and every plugin must agree on
what a verb means, where categories are deliberately deployment-defined and opaque.

**Gated on the build-versus-adopt question**, since this work reimplements a permission model at
least two existing engines already provide.

## Write versus read access: requirement stated, mechanism unchosen

Two independent axes, and conflating them is the trap. Provenance (a submitter reaches what they
submitted) is not expressible under resource-level enforcement, since resources are a flat list with
no parent relationship. Consent (a submitter may not be entitled to read the sensitive content of
what they submitted) is what category grants handle.

Neither substitutes for the other: provenance scoping hands a community liaison exactly the records
the consent case is about, and withholding categories gives every submitter the same view of the
whole resource.

Three MVP paths recorded, none chosen: a resource per submission, membership without category grants,
or no automatic read. The second was proposed and then withdrawn as contradicting the stated intent.

**Recorded independently of the choice:** any inheritance rule must be evaluated at request time
rather than written as grants copied at submission time. Copied grants outlive the access that
produced them, so revoking study access leaves a reader on every submission made while they held it,
and copied grants turn a later narrowing into a migration.

## Invitation flow settled

The pending-grant migration fires on registration keyed to the invited address, which leaves an
invitee holding an account under a different address waiting indefinitely with nothing to resolve.

An invitation link closes that gap under one constraint that is the whole design: **the link binds
identity and never creates or activates a grant.** Binding-not-granting is what makes single-use and
short expiry sufficient, since a link that could activate access would make the invited mailbox the
authorization boundary. Group grants have no acceptance step, so this applies only to grants issued
to an individual address.

## Why categories require all rather than any

The rule appeared in two files with justification in neither, and was wrongly attributed in
discussion to OCAP. The actual reason is general: a restriction another restriction can bypass is
not a restriction, so holding one category must not reach a resource carrying a second. Community
governance makes the consequence severe rather than creating the requirement.

Recorded alongside it: restrictions compose monotonically, so adding a category can only narrow and
never widen, letting a deployment introduce a classification without auditing existing grants; an
unrecognized category fails closed rather than remaining reachable through some other held category;
the cost is the split requirement; and **categories are restrictions rather than partitions**, so a
future need to select part of a resource is a different mechanism rather than a reinterpretation of
this one. Unexercised in v1, which defines one category, and therefore unvalidated by the first
deployment.

## Extensibility constraints for a design-ahead, build-incrementally approach

Three choices that keep deferred work additive rather than reshaping: express grant authority as a
single function even though v1's answer is always the owner, so adding a custodian branch is one
change rather than a hunt; carry capability in the token from v1 with its single value, so later
levels change a value rather than adding a field to a published contract; and keep categories in the
token, since record-level narrowing needs them and removing then restoring is two contract changes.

### No per-record classification exists to enforce on

The access-classification field cannot carry record-level enforcement, for a reason stronger than a
mapping shape.

| Observation | Where |
|---|---|
| `file_access` holds a single scalar, not an array | Live clinical document |
| Every clinical record carries the same value, `open` | Reported from the deployment |
| `file_access` is absent entirely | Environmental catalogue |
| The optional root `files` property, present only when a record has a sequencing file attached, does not carry the value either | Environmental catalogue |

Four consequences, in increasing order of how hard each is to undo:

1. **Uniform value.** A field that has only ever held one value carries no evidence that the pipeline
   sets the other value correctly. It has never been exercised as a discriminator.
2. **Absent on one of two catalogues.** The catalogues differ in grain, one file-centric and one
   analysis-centric, so the absence is a modelling consequence rather than an oversight.
3. **The absence fails in the permissive direction.** Record-level enforcement needs a negated
   containment expression. A clause against a field absent from the mapping matches no documents, and
   negating it therefore matches every document. The construction does not degrade to a denial on the
   environmental catalogue, it degrades to an allowance. This follows from the query semantics rather
   than from a test that was run, and is worth confirming before anyone relies on the field
   defensively.
4. **Nothing owns it.** The field is written by the submission and indexing pipeline. No invariant
   ties it to any grant decision, so an authorization outcome would depend on a value a data pipeline
   can change without the authorization system knowing. An authorization input needs an owner and a
   governed write path, and this field has neither.

**The blocker moved rather than lifted.** It was a mapping shape, which a mapping change fixes. It is
now the absence of a trustworthy per-record classification on either catalogue, plus the absence of
anyone owning its production. The second is an unmade data-model decision and sits further from MVP
than the first.

### What would have to be true for record-level to become available

All three, none of which hold:

| Condition | Status |
|---|---|
| A per-record classification field exists on both catalogues, mapped `nested` | Absent on both |
| Something owns setting it, on a write path governed by the same authority that grants access | Undesigned |
| Its cardinality and permitted values are declared rather than inferred | Undeclared |

**If per-record granularity is needed before field-level work begins, the resource is the unit to
split, not the record.** A narrower resource, such as a study paired with a data type, keeps the flat
containment clause and needs neither a mapping change nor a new classification field. This is the
separate mechanism already noted for selecting part of a resource, since categories restrict rather
than partition.

## The environmental record: the resource key is not the same field

An environmental record was read directly, which is the catalogue whose mapping was never located.
It is shaped like a submission record rather than an indexed one, carrying `entityName`, `isValid`,
`systemId` and a conditional `files` array around a flat `data` object, so the indexed form may

**There is no `study_id`.** The grouping field is `organization`, holding a short project code, with
`sample_collection_project_name` carrying the same grouping in long form. The clinical catalogue keys
on `study_id`; this one does not have that field at all.

**So the resource key is per-catalogue configuration, not one field name.** The v1 enforcement
clause is a positive containment on the field naming the resource a record belongs to, and which
field that is differs between the two catalogues in the very first deployment. A plugin configured
with a single global field name would produce a clause against an unmapped field on one of the two,
which is the fail-open direction already documented. The field name belongs in per-queryable-type
configuration, verified at startup rather than assumed, alongside the mapping-shape check.

**Nothing prescriptive, again.** Across roughly 120 fields there is no access level, no restriction
marker, and no classification of any kind. This is the third independent confirmation that
enforcement here reads descriptive fields only, and it closes the question of whether the

**`files` is conditional and shallow.** An array of objects carrying an object identifier, a file

the download enforcement surface applies per file object rather than per record, and records without

scalars, with no nesting.

**A third meaning of steward, this time inside the data.** The records carry
`data_steward_contact_name` and `data_steward_contact_email`, naming a person to contact. That is

## Admin model, corrected twice

The first correction was mine to make and I made it too hard. A clarification that a system
administrator should not necessarily read records was recorded as reading no records at all, and the
hedge in it was doing work. Self-grant exists: standing data access is none, and an administrator may
grant data access to themselves explicitly.

**What changes over time is the approval, not the capability.** No approval is required in MVP; one
will be once community custodianship is implemented.

**The design consequence is worth more than the correction.** A self-grant is a grant, and a grant is
issued by a grant authority: a resource's owner for the resource, a category's custodian for the
category. Writing MVP's self-grant as an authority check carrying an administrator exception means
the later change removes a branch rather than introducing an approval workflow where none existed.
Writing it as a bare write means building that workflow later against code that assumes no approval
step. Same MVP behaviour, materially different cost when custodianship lands, which is the constraint
this whole design is being held to.

**Unsettled: whose approval.** Stated as the owner's, while the trigger for needing it is
custodianship, which points at the custodian. The grant-authority framing admits both without
choosing: an administrator self-granting into a resource carrying a category needs the resource's
authority and that category's authority, and which apply follows from what the resource carries.

Granting to others is a separate question and is unchanged: sharing remains exclusively the
data-plane roles', which is what the portal flows say.

## The token contract, reworked three times and settled

A resource's entry is now a plain list of grants, each naming one category and the capabilities held
on it. No role name, no detached capability list, no empty-list case.

    "STUDY_A": [ { "open": ["view", "download"] }, { "controlled": ["view"] } ]

**Open content is a category.** This is the load-bearing change and the reason the earlier shapes
were hard to reason about. A detached capability list existed only to cover a resource's
unrestricted portion, which presumed that portion was a baseline sitting outside the category
system. A baseline is what the superseded subtractive model needed; additive rendering does not have
one. With open content named in a grant like anything else, every reachable record is reachable
because a grant says why, and the empty-list case disappears because holding no grant is what
absence already means. The accepted cost is that categories stop being optional: a resource carrying
none is ungrantable.

**No role name travels.** Roles are how access is authored. The controller resolves a role to
capabilities at issuance, so no plugin learns what a deployment means by `member`. Ownership is
absent for a second and independent reason: it is a management capability enforced by Usher's own
API, so an enforcement payload has no use for it. This is the conclusion an earlier sketch reached
backwards by inventing a `manage` flag before asking what would consume it.

**An anonymous role defines the baseline, and may grant nothing.** Where it is empty, unauthenticated
callers receive an empty grant set and even open data requires registration, so whether open means
publicly readable or registration-gated becomes a deployment decision rather than an assumption in
this design. It also retires the synthetic `public` role, which had described itself in prose because
there was no field to put a capability in.

**The confusion was the documents', not the reader's.** A worked example in `permissions-model.md`
described the subtractive model in full, with no marker, computing exclusion sets from a full
category set. Under the two models the same token field means opposite things. The example is
rewritten additively: neither user's unreachable data is excluded by a clause, it is unreachable
because no clause selects it.

**Vocabulary:** `view` rather than `read`, matching what the portal distinguishes. The full set is
still the permission-assignment work in the RABAC alignment note.

## Corrections made while doing this

**The RABAC alignment note proposed a shape less expressive than the paper.** It had a `permissions`
list beside a `categories` list, which implies their cross-product. The paper was fetched and
confirms each permission carries its own filtering condition, and that distinct operations may be
permitted under different constraints. Pairing capability with category is the faithful
pre-resolution; two independent lists cannot express read on one category and read plus upload on
another, which this project had already asked for.

**Manufactured resource keys were rejected.** Encoding a category into the resource key was floated
as the route to separately grantable segments. It is the duplication the role-and-attribute hybrid
exists to avoid, reappearing on the resource axis, and it does not work regardless: no field holds
the manufactured value, so a positive containment cannot select it. Splitting the resource key is
only enforceable along an axis the data already expresses.

**"Record-level narrowing is unavailable" was too strong.** Narrowing by predicate over existing
descriptive fields is available now on both catalogues. What is blocked is narrowing by category,
which needs a per-record category field mapped `nested`. The two had been carried under one name,
which is the same defect class as the steward collision.
