## Granting is one function; the data's restrictions are the last gate

An administrator may grant permissions to themselves or to anyone else, permissions meaning more
than reading data: assigning a role, conferring a capability. What no initiator bypasses is what the
data requires, so a grant passes authority first and the data's restrictions second, and who started
it changes only the first stage.

**A recorded invariant was stricter than intended and is replaced.** It required every category to
have at least one custodian, closing the empty-approver-set hazard by construction. The chosen
control is a warning instead: a category may exist unassigned, and the system must have warned that
dataset's owners, so an unguarded category is a known state rather than a discovered one.

**This is the one deliberate permissive failure in the design**, which is worth naming because
uncertainty withholds everywhere else. Two implementation consequences follow: the warning must be
delivered and recorded rather than displayed, since a control depending on someone reading it needs
evidence it was sent, and access reached this way needs an audit event distinguishable from an
approved one.

Still open: whether appointing a custodian needs a second party, since an administrator who may
appoint can appoint themselves and then approve their own grant.

## The aggregation-path requirement conflict is settled

It was the last open conflict against the business requirements, and it dissolves rather than
needing work.

The defect composes an authorization filter disjunctively where the authorization field sits at
nesting depth two or greater. The settled filter is a single positive containment clause on the
field naming a resource, flat and at depth one in both of the first deployment's catalogues. A
single clause also has no siblings, so the `should` versus `must` composition question does not
arise rather than being answered.

Two conditions hold it there and both were already required: the plugin establishes the field's
mapping shape at startup and refuses to enforce where it cannot, and record-level narrowing stays
post-MVP, since a per-record category field is exactly what would place an authorization field deep
enough for the defect to return. That is a real constraint on the post-MVP work rather than a
coincidence, and it is now recorded there.

**What remains is verification rather than design.** A value-returning surface can discard the
filter altogether, which no mapping depth affects and no configuration reveals, and which was found
once in practice by comparing counts rather than by reading code. The conformance case per
value-returning surface closes that, and the roadmap entry it previously lacked now exists in place
of the conflict entry.

Requirements status: no open conflicts remain, and the two aggregation requirements read as met

## Blocker 7, the EGO token TTL, is resolved

Its action item said to confirm with whoever has access to the EGO deployment config. The
deployment's own Helm values are checked out locally, so it was read rather than asked for, and the
figures agree across the iMS production and development environments and the Overture demo
environment: a 3-hour access token and a 12-hour refresh token.

**The migration baseline it existed to establish is satisfied by a wide margin.** The designed
grants-token lifetime is five minutes, a thirty-sixth of the access token it replaces, so there was
never a tension to resolve.

**The refresh token is the number the migration should be measured against**, not the access token.
A revoked principal keeps minting access tokens until the refresh token stops working, so the
current worst-case window is bounded by 12 hours unless revocation invalidates stored refresh
tokens server-side. EGO persists them, so it may. Recorded as the one confirmation left, since the
difference between 3 and 12 hours is the difference between a good improvement and a large one.

**A larger window than either sits outside both.** API tokens are a separate long-lived credential.
The iMS environments do not set their lifetime, so a chart default applies that is not visible from
here; the demo environment sets it to 3650 days, which shows the range. If iMS issues them for
programmatic access they bypass both windows, and that use case needs a deliberate answer rather
than an inherited one.

**Three documents quoted three different Usher TTLs.** The canonical five minutes in the token
document, a fifteen-minute ceiling recommendation in the admin model, which is compatible, and a
fifteen-minute *default* in the blocker list, which was never the design's number. Corrected.

Also visible in the same values and relevant to a different risk: iMS's EGO already has its
Keycloak UI integration enabled, with the token-exchange setting present but commented out. The
feasibility table lists the portal's EGO-to-Keycloak migration as an unknown timeline; login
delegation is evidently further along than token exchange, which is a more precise starting point
than "unknown" for whoever owns that dependency.

## Why EGO's tokens are three hours, and what it forecloses here

The figure has a cause: submitters run large uploads that outlive a short token and fail partway, so
the lifetime was raised until they stopped failing. That reframes it from a configuration value to
inherit into a symptom to avoid, and it was worth learning before the design lock rather than after.

**It is a scope error rather than a duration error.** A credential authorizing everything a
principal may do, platform-wide and across reads as well as writes, was lengthened so that one
long-running write would survive. Scope and duration trade against each other: broad or long-lived
is defensible, broad and long-lived is the worst of four combinations, and the narrow long-lived
authorization the upload actually needed was never the thing extended.

**Most of the exposure is absent here by accident of shape, and the residue is the real work.** The
grants token is fetched by the bridge and cached there, so no principal holds one and its expiry
aborts nothing: the bridge re-exchanges and the controller re-evaluates current policy when it does.
What remains is the principal's own identity token, held by a client for the duration of an upload,
where any step needing a valid one can still fail partway. The problem moves rather than vanishing,
which is exactly the kind of thing that gets solved later by lengthening something.

**The target is better than parity, not equal to it.** An operation authorized as an operation, with
a scope naming what it may touch and revocable in its own right, means a withdrawal reaches work in
flight. Today an upload in progress cannot be stopped short of three hours.

**Upload is a third enforcement surface and duration is what distinguishes it.** Searching is
instantaneous, downloading is short, and only submission runs long enough for a credential to expire
underneath it. The design had nothing on this: `upload` appeared only in provenance definitions.
Recorded as a decision plus a roadmap item covering where re-authorization happens, whether an
upload session is revocable in flight, and which plugin owns it.

## Legibility: the density threshold measures the wrong defect

The convention states density as sentences over thirty words. Asked whether to tighten it to twenty,
the developer pushed back on the metric rather than the number: the interest is in not relying on
overly-compressed abstraction where something can be said plainly.

Three candidate defects were measured across six documents rather than assuming length was the one.
Nominalization used as a sentence's actor appeared once or twice per form. Concepts squeezed into
hyphenated coinages were almost all filenames or real terms of art. **Abstract back-reference was
the defect: 56 instances**, concentrated in "the shape" at eleven, "the mechanism" at eight, "the
thing" at eight and "the premise" at six. A reader is handed a placeholder noun and has to
reconstruct which earlier idea it points at.

**Length did not correlate.** Sentences inside the threshold still read as abstraction, and some
outside it were long and perfectly clear.

Sixteen instances were genuine defects and were fixed; the remaining twenty-nine are cases where a
placeholder sits one clause from its concrete referent, which reads fine. That ratio is the useful
part: **the grep finds candidates and judgement decides**, so this belongs in a convention as a
check that raises candidates rather than as a rule that condemns matches.

Two sections written earlier this session went from seven-of-sixteen and six-of-fifteen long
sentences to zero. The mechanism was the same in both passes: three ideas chained per sentence with
commas and relative clauses. Breaking the chains raises the sentence count while the prose gets
plainer, which is why a count of long sentences is a poor target on its own.

**The convention's own warning landed on the agent that had read it.** The density note recorded that
the sections written while proposing the convention were denser than the file they went into. Two
weeks later, sections written here after reading that note ran forty to forty-four percent long
against a nineteen percent file average. Reading a convention does not cause it to be applied to
your own output, which makes this a convention-design problem rather than a discipline one.

Sent to the agentics owner along with two implementation gotchas: a regex stripping fenced code
still admits indented code, which produced a phantom eighty-five-word sentence, and splitting
sentences per line returns zero on hard-wrapped prose because paragraphs must be reassembled first.

## What the agentics exchange produced, and two failures of the reviewer

The legibility finding travelled and came back sharper. Recorded in
[../docs/atlas/roadmap/doc-review-patterns.md](../docs/atlas/roadmap/doc-review-patterns.md) rather
than only here, since that file is where these classes live.

**The discriminator worth keeping is effort against ambiguity.** A rule reduces one or the other, and
which one decides whether it applies to documents written for people or for agents. Effort is a
human cost, since a person scans and scrolls back while an agent reading linearly already holds the
referent. Ambiguity costs everyone. That explains the back-reference ratio structurally rather than
empirically: a referent one clause away costs effort and only to a scanner, while an absent or plural
one is ambiguity. The twenty-nine left standing were the first kind, the sixteen fixed were the
second.

**Two failures were the reviewer's, not the corpus's.**

The pass correctly left the agent-facing instruction files alone, but by inheriting an exemption this
project's density table already recorded, not by any judgement in the method. A correct result
produced by an inherited constraint is indistinguishable from a correct method, and the moment the
constraint is absent is the moment nobody is checking.

A count from the peer's corpus was relayed to the developer as established fact, with an argument
built on it, before either side had checked its scope. It was scoped to agent-facing files and the
instances were not defects. A number invites this because it looks like a fact rather than a claim.

**The method is now written down, which it was not.** This repository has no check script, so every
pass today was ad-hoc bash. Four requirements are recorded, each of which was got wrong once during
the work: one shared extraction, three states for a block marker, paragraphs assembled before
sentence splitting, and both fenced and indented code stripped. Plus the rule that a moving count
gets an item opened rather than the total trusted.
