## iMicroSeq Portal UI cross-session exchange

Completed a two-turn exchange with the iMicroSeq Portal UI session (virusseq-portal-2c) on the
current EGO/Keycloak integration architecture. Findings relevant to Usher design:

**Two-part migration surface for iMS.** Not a single client-side migration, but two distinct surfaces:

1. `virusseq-api` (gateway) validates the JWT once, at issuance, inside `POST /token` (OAuth code
   exchange). Uses `jwks-rsa` + `jsonwebtoken.verify()`. This layer needs to accept Keycloak JWTs
   when EGO is replaced, a gateway migration independent of Usher's enforcement layer.

2. Per-request enforcement does not exist today. The gateway just forwards the session cookie to
   EGO's own `/api/v1/users/me` on `GET /user-info`; no JWT re-validation on proxied calls.
   Usher's per-request enforcement via usher-bridge is additive, not a replacement of existing
   server-side auth, because that layer does not currently exist.

**No refresh mechanism.** On token expiry, `isValidJwt` fails, the app clears localStorage and
drops auth state, user must re-login. No silent refresh, no scheduled poll. Usher's TTL design
must account for this UX baseline; the bridge cache window and what happens on expiry should
match or improve the existing re-login behavior, not introduce a new flow without UX design.

**Keycloak version gap confirmed.** iMS portal's dev Keycloak is 17.0.1 on the legacy WildFly
chart (codecentric/keycloak, unsupported since June 2022, removed at Keycloak 21). Overture infra
runs 26.3.3 on keycloakx. Upgrading iMS dev or repointing to the infra Keycloak is an
infrastructure prerequisite for migration: it shifts the `/auth` base path, the issuer string,
and the JWKS and admin API URLs. Not a Usher design blocker, but a prerequisite on the iMS side
that needs an owner.

**Portal-ui env vars (EGO-related):**
- `NEXT_PUBLIC_EGO_API_URL`, `NEXT_PUBLIC_EGO_CLIENT_ID`, `NEXT_PUBLIC_EGO_PUBLIC_KEY`
- `NEXT_PUBLIC_KEYCLOAK` (base URL)
- Scope authorization vars: `NEXT_PUBLIC_SCOPE_ENVIRONMENTAL_PREFIX_WRITE/_SUFFIX_WRITE`,
  clinical equivalents, `NEXT_PUBLIC_SCOPE_ENVIRONMENTAL_ADMIN_WRITE`,
  `NEXT_PUBLIC_SCOPE_CLINICAL_ADMIN_WRITE`, `NEXT_PUBLIC_SCOPE_STUDY_SVC_WRITE`
- Feature flags: `NEXT_PUBLIC_ENABLE_LOGIN`, `NEXT_PUBLIC_ENABLE_REGISTRATION`

All `NEXT_PUBLIC_`-prefixed; no server-only secrets on the portal-ui side (static frontend).
