# 2026-09-21

## The payload is a type now

`PermissionsPayload` is written member by member in security-workflow.md, under "The payload as a
type", with the reasoning attached to each. It lands in the design corpus rather than a source tree
because no package layout is decided; the file it eventually occupies is a layout question and blocks
nothing.

It was written before any fixture or mock so that both consume one definition. A mock built
independently of the fixtures can be right in a way the tests never check, which is the failure this
ordering avoids.

## Two members existed only as prose

The version-negotiation decision said the payload declares its own version. Four places said the
token records a category version per resource. Neither had a name, a type or a home, so a type had to
supply all three. `payloadVersion` justified its home and kept it.

## Category versions came out of the token

The fast path was comparing the wrong artifact. The question it must answer is whether *the cached
payload* is computed under current categories, and the token is a different artifact that coincides
with that payload only by circumstance.

They now live in the cache entry, which already held the earliest grant expiry alongside the payload,
so this is one more field on a structure that exists rather than a new mechanism.

Three things follow:

- The payload loses its only member no plugin reads, and with it a key-set invariant that a validator
  would otherwise have had to enforce against `permissions`.
- The freshness test stops reading anything the request supplies. The substitution it closes is narrow
  and low severity: presenting a valid IdP token together with another principal's expired token, one
  carrying versions that happen to match current, would return a payload computed under superseded
  categories for one more TTL. Forging a token needs the per-application key, and a bridge holding
  that key can already mint payloads directly.
- **A refresh becomes the same call as the first exchange**, the expired token having had no other
  stated purpose. The bridge sends an IdP token and its audience identifier in both cases, so it has
  one operation rather than two and the fast path is entirely internal.

## What `generatedAt` is for, now that it is not in the fast-path test

It records when the permissions were computed, and a reissue deliberately does not change it, so it
and `iat` come apart by exactly the span a token has been served from cache. That is a diagnostic and
an audit correlation rather than an input to any decision. Whether anything should act on it, such as
a bridge forcing a recomputation once the underlying computation passes some age, is open and
unbuilt.

## The type was checked, not just written

It compiles under `--strict`. Every token example in the corpus satisfies it, including the
field-nesting and artifact shapes from permissions-model.md that no token example had yet carried.

It rejects an empty action list, an action belonging to another entity, an action outside the
vocabulary, `payloadVersion` missing, and `sub` omitted rather than set to `null`. That last one is
worth keeping: anonymous is an explicit `null`, and an absent `sub` is a malformed token rather than
an anonymous one.

Action lists are non-empty by type, through a `NonEmpty` helper. An empty list would mean what
absence already means, which is the same argument that gives resources no empty-entry case. The
`permissions` map itself may be empty, which is a registered principal holding no grants at all.

## The token is not an OAuth access token, and three tests say so

Recorded in decisions.md as one entry rather than three, because each has been asked as "why not just
use the standard one?" and each answers the same way.

**RFC 9396 `authorization_details`** is the registered claim for structured authorization. Right
family, wrong shape: its `actions` is a flat string array, so the entity axis has nowhere to go but
back inside the action string as `record.read`, which is the collapse the entity level exists to
undo. Field categories fare worse, since RAR prescribes separate objects rather than nesting. The
deciding argument is that RAR's value is discoverability by relying parties an issuer does not
control, and this token is encrypted to one application's key and read by nobody else. **The
condition is written down alongside the conclusion**: revisit if a third party ever reads the payload.

**RFC 9068** requires seven claims for a JWT access token and five are already present, which nobody
aimed at. `client_id` would always equal `aud` here, since the bridge requests a token for the
application it runs inside. `jti` exists there to let a resource server detect a token a client
replayed, and no client presents this one. `sub: null` has no counterpart, an authorization server
with no end user setting `sub` to the `client_id`. Its `roles`, `groups` and `entitlements` look
applicable and are not, since no role name travels in this token by decision.

**`generatedAt`** has no registered equivalent and two precedents for its shape: `toe` in a Security
Event Token (RFC 8417 §2.2) and `auth_time` in OIDC Core §2, both a second timestamp recording when
the underlying thing happened, unmoved by a reissue that resets `iat`. `updated_at` reads closest and
must not be reused, being a UserInfo claim about the end user's own profile record.

## `typ` is `usher+jwt`

Explicit typing is BCP 225 §3.11. The value is deliberately not `at+jwt`, which would assert
conformance to a profile this token misses three requirements of, making it the confusion the
parameter exists to prevent. Defence in depth rather than a hole closed: Usher issues one JWT kind,
API keys are opaque by decision, and a three-part JWS under asymmetric keys against a five-part JWE
under a per-application symmetric key already satisfies §3.12 through the key separation alone.

Recorded alongside it: the JWE protected header is authenticated but not encrypted, so `typ` and
eventually `kid` are readable by anyone holding the token. Neither says anything about grants, and
nothing that does may be added there.

## Three BCP 225 items left open, now on the list

§3.1 (pin `alg` and `enc` on read, not only on emit), §3.6 (never `zip`), §3.10 (`kid` handling,
which arrives with key rotation). Logged in to-discuss.md under Token contract at MEDIUM, together
with four LOW details that have no stated answer: clock skew, `aud` string versus array, `nbf`, and a
token size bound. Leaving them open while citing the same BCP for the item that was taken is the part
that needed recording.

## `principals.json` is drafted, with a validator

At `.dev/design/conformance/`, in this repository rather than the integration repository, because
phase-1.md names that file Usher's to own and owning a file is separate from hosting it.

28 entries from the 29 cases. Case 25 is omitted with its reason recorded in the file: a grant
pairing `record.delete` with a field category is refused at writing, so no token exists to put there
and the case belongs to Usher's own schema tests. Cases 21 and 22 carry ordinary payloads marked
`implementable: false`, since neither withholding nor the multi-category subset test can be expressed
in a payload at all, so what is unimplementable lives in the expectations rather than here.

**Two deliberate divergences from the case table**, both in the fixture README. Roles expand against
the seeded matrix rather than the table's local reduction (`viewer` as `read` alone, `curator` as CRUD
alone), because a fixture claiming real tokens has to hold the real role while the table's reduction
stays correct for what it teaches. And temporal claims are a fixed reference instant, since the corpus
scopes token verification out.

## A TypeScript type cannot validate the JSON, which is worth knowing

Typechecking the fixtures against `PermissionsPayload` fails for a reason that is not about the
fixtures: importing a JSON file infers a union of object literals, so the entry whose `permissions` is
empty widens its siblings' keys to `undefined` and the array stops assigning. The check reports a
defect in the importer.

`.dev/check-fixtures.py` does the job instead, and carries two rules the type cannot. Action lists are
non-empty, which the type says through `NonEmpty` but only for literals. And no member may be named
`categoryVersions`, so a fixture cannot teach an adapter to expect a member the controller does not
emit.

**Fifteen inversions, all red, control green.** Empty action list, action outside the vocabulary,
cross-entity action, unknown entity, `categoryVersions` present, `sub` omitted, `payloadVersion`
omitted, empty category map, empty entity map, `field` as a list, empty field map, `exp` not after
`iat`, duplicate id, repeated action, missing case number. Run before claiming the validator works,
because a checker passing on its first run says nothing about whether it would fail.
