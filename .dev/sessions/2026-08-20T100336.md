## Blocker #3: grants payload schema design exploration

Explored SQON-as-grants-format vs. structured categories as the shape for resource grants inside the constraint token. Key findings:

**SQON-as-grants:** grants are stored as SQON predicates directly. No translation layer in the plugin; the injected filter is the grant verbatim. But Usher's PAP becomes aware of field names (schema-coupled), and token size grows with grant complexity.

**Structured categories:** grants stored as `(resource, category)` pairs. Usher stays field-agnostic. Plugin holds the translation table (category -> SQON). Adds a deployment-time configuration step per integration.

**Nested grants (two-dimensional access control):** the richer model: each grant carries a `filter` (SQON predicate for row selection) and a `fields.exclude` (list for column-level restriction). Emerged from the iMS use case: "all fields except X Y Z in studies ABC and DEF".

**Field-exclusion vs. SQON:** ES `_source.excludes` applies uniformly to a query result; there is no per-row field exclusion. Two approaches when multiple grants have different field restrictions:

- Option A (conservative union): take the union of all exclude lists, single query. Safe; over-restricts in the general case (user may see fewer fields than entitled to in a given row).
- Option B (per-grant queries): N queries, one per grant, each applying its own excludes, results merged. Correct; N round trips.

Recommendation: Option A for v1. Correct in the worst case (never leaks), and the over-restriction is bounded by how divergent grants are in practice for a given user.

**iMS access model confirmed:** program/study scoped (same concept, different label). Deeper granularity is the goal: a user granted access to studies ABC and DEF with certain fields excluded is the concrete target shape.
