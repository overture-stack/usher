## Design decisions documented (resumed from prior context)

Reviewed iMS UAC BRD and user flows. Explored the studies management service to understand
EGO's API surface. Documented all resulting decisions across eight design files.

Key decisions recorded:

- **Accept/decline is the default sharing flow.** Grants enter `awaiting_acceptance` state until
  the grantee explicitly accepts. Auto-accept is a configurable flag, off by default. Pending
  grants for unregistered users are keyed by email; on registration they migrate to
  `awaiting_acceptance` under the user's Keycloak ID.

- **EGO is replaced in full, not integrated.** Usher absorbs all EGO authorization
  responsibilities. The studies management service is retired; its operations become Usher admin
  API calls. Migration path documented in `admin-model.md`.

- **User IDs (Keycloak `sub`) are the primary identifier.** Email is stored for display only and
  used as a key only in `pending_grants` (pre-registration state). Email resolution for display
  happens at the portal layer via Keycloak admin API.

- **Usher is the resource lifecycle management layer.** Resource creation, metadata, membership,
  category assignment, and visibility policy are all Usher responsibilities. The studies
  management service is retired once Usher's resource management API is live.

- **SONG's role is narrowed to file metadata.** Usher is the source of truth for resource
  metadata; SONG handles file manifests and genomic object references. Deployments without SONG
  are fully supported.

- **"Study" and other domain terms are deployment vocabulary.** Usher's model uses "resource"
  throughout. iMS's "study" maps to a resource where the plugin config uses
  `fieldName: "study_id"`.

- **Platform admin plugin bypass** is a plugin-layer option (not grant-based). The plugin
  detects `usher-platform-admin` role and skips SQON filter injection. Every bypass is logged.
  Disable for PHI deployments requiring all access to be grant-based.

- **Overlapping cohort OR/AND semantics are moot for iMS** (each sample has a unique `study_id`;
  no record belongs to more than one resource). The question remains open for generic deployments.

Files updated: `glossary.md`, `decisions.md`, `permissions-model.md`, `admin-model.md`,
`to-discuss.md`, `architecture.md`, `plugin-integration.md`, `docs/concepts.md`.

## iMS Arranger catalogue analysis

Read iMS dev Arranger configs at `virusseq-infra-sd4h/envs/dev/virusseq-dev/stateless/helm/`.
Two catalogues found:

**arranger-clinical** (`clinical_centric` index, `documentType: "file"`)
SONG-derived structure (`analysis.*`, `analysis.samples.*`). Cohort-grouping field is `study_id`
at the top level of every document. This is the confirmed fieldName for usher-arranger plugin
config on the clinical side: each Usher resource corresponds to one `study_id` value.

**arranger-environmental** (`environmental_centric` index, `documentType: "analysis"`)
Flat `data.*` structure, no SONG hierarchy. Root-level `organization` field is a denormalized
organizational affiliation injected at index time, not a domain grouping concept. The study
equivalent is nested in `data.*`; most likely candidate is `data.sample_collection_project_name`.
Awaiting submission service schema to confirm. Environmental data may also be open-access by
design; needs a deliberate decision before plugin config can be written.

**Design constraint documented**

A single Usher controller serves both catalogues. The usher-arranger plugin must be
catalogue-aware: grants scoped to a clinical resource must inject SQON filters only on
`clinical_centric` queries, never on `environmental_centric` queries, regardless of whether the
same fieldName appears in both indices. The plugin config maps resources to specific catalogues;
Usher itself has no catalogue concept.

"Catalogue" is Arranger vocabulary only. Other Overture services (Lyric, SONG, Score, Lectern)
will have their own plugin config shapes. Usher's contract ends at the `GrantsPayload` boundary;
each plugin's design doc (in that service's repo) owns its config schema.

Documented in `plugin-integration.md` (Usher). Arranger-side detail (catalogue-scoped config,
leak prevention, iMS fieldName candidates) relayed to arranger-21 for `arranger/.dev/docs/usher-plugin.md`.

## EGO migration scope clarified in admin-model.md

Step 5 of the EGO replacement migration plan updated. The migration surface is two categories:
(1) services that call EGO endpoints directly, and (2) authorization callbacks that read
EGO-populated request context -- these live in host application repos, not in the data service
repos. Data services that perform no authentication themselves (e.g. a search-server relying
on host-supplied context) are not in scope as shipped; the host code building that context is.

Also noted: "performs no authentication" is a distinct category from "authenticates via a
different mechanism" -- relevant when enumerating migration scope.

## Submission service exchange: token structure and migration findings

Direct exchange with the iMicroSeq submission service confirmed three findings about the current
EGO-backed token structure. These informed two new open questions added to Usher design docs.

**Token structure.** The submission service decodes tokens into `EgoJwtData`, which declares only
`context.user.{email, status, type}` and `context.scope` -- no `iss` or `sub` field is typed or
checked. `context.scope` contains org-scoped permission strings built from configurable prefix and
suffix env vars; "organization" is the only named access unit in the codebase. "Study" does not
appear.

**Issuer check absence.** `jwt.verify` passes no `issuer` option. The gap is key-confusion rather
than forgery: a valid RS256 signature proves the token was issued by the holder of the
corresponding private key, so forgery without that key is not possible. What the missing check
permits is accepting tokens from any issuer whose key happens to match `AUTH_PUBLIC_KEY`. In the
migration context, the implication is concrete: if Keycloak uses its own key pair (the normal
case), Keycloak-issued tokens will fail verification against the existing `AUTH_PUBLIC_KEY`. Key
rotation is the migration event at this service -- not just a config repoint but a required change
to `AUTH_PUBLIC_KEY`. This should be called out explicitly in admin-model.md step 5.

**Status check.** Only `'APPROVED'` is referenced as a recognized value for `context.user.status`.
No enum of other possible values is defined in the codebase; all non-approved statuses produce
the same 403 response.

**`sub` identifier absent.** The current token carries email but not Keycloak `sub`. Usher
uses `sub` as the primary identifier for all grants and memberships. Any Usher integration at the
submission service, or any submission-time grant creation (write-vs-read option 1 or 2), requires
`sub` to be present in the token. This is a token schema change that must be coordinated with the
IdP migration.

## New open questions added

**Write vs read access** added to `permissions-model.md`. Three options: (1) submission creates
full read grants for the submitter; (2) organizational membership grants read access to all
records submitted by that organization; (3) no automatic read access -- submission and read access
are independently governed. The correct answer has OCAP implications and must not be resolved in
isolation. See write-vs-read-access section for the full decision surface.

**Authorization unit chain** added to `plugin-integration.md`. The resource ID Usher tracks must
be traceable through the full pipeline: submission unit (org scope) to data service unit (study or
cohort ID) to indexed field to plugin filter field. Any broken link is silently misconfigured.
Each deployment must verify this chain at plugin configuration time; Usher cannot validate it.

## Submission service: full EGO integration writeup received

The iMicroSeq submission service produced a detailed writeup of the current EGO integration:
`iMS-submission-service/.dev/docs/auth/ego-integration-current-state.md`. Integration-specific
detail lives there. Key Usher-design-relevant findings from that writeup:

**Read access is currently ungated.** `allowedReadOrganizations` is hardcoded to `[]` and was
never implemented. Additionally, `AUTH_PROTECT_METHODS` defaults to `POST,PUT,DELETE`, so `GET`
bypasses auth entirely by default even when `AUTH_ENABLED=true`. The service currently has no
read authorization at all. A Usher integration at the read layer would introduce read enforcement
for the first time, not replace an existing mechanism. This is relevant context for the
write-vs-read design decision but does not resolve it: the design question (should submission
create read grants?) is independent of what the current service does.

**Key rotation is the migration event.** Confirmed: `jwt.verify` uses `AUTH_PUBLIC_KEY` with no
`iss` check. The gap is key-confusion (any issuer verifying against the same public key would be
accepted), not forgery. Keycloak uses its own key pair; migration requires updating
`AUTH_PUBLIC_KEY` at this service as a concrete migration step.

**Narrow but non-trivial migration surface.** The abstraction boundary is partial: `verifyToken`
is a single chokepoint both this repo's `authMiddleware` and Lyric's `customAuthHandler` call.
But EGO-specific assumptions leak into three places (EgoJwtData shape, scope-string parsing
convention, allowedReadOrganizations). Swapping auth requires editing `verifyEgoJwt.ts`,
`common/auth.ts`, and `envConfig.ts`, plus verifying both call sites. The Lyric-internal route
coverage via `AppConfig.auth` was flagged as an assumption (not verified against Lyric source).

**`shouldBypassAuth` has two independent mechanisms:** `AUTH_ENABLED=false` globally, and
HTTP method not in `AUTH_PROTECT_METHODS`. Both are genuine feature flags.

No test coverage for any auth path at this service. Node:test hangs on provider import without
a live Postgres connection, blocking isolation tests of the auth functions themselves.
