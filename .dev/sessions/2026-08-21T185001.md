## Decision: resource-level enforcement for MVP

Recorded in `.dev/design/decisions.md`. A record is visible if the principal holds every category
carried by the resource the record belongs to, so the emitted filter is one positive `in` clause on
the resource key and no category field appears in the index.

This resolves a genuine ambiguity in `permissions-model.md`, which contains both a resource-level
reading (the visibility rule's own wording) and a record-level one (the exclusion mechanism and the
worked example). Record-level tagging is deferred alongside SQON-scoped grants; they are the same
capability, narrowing within a resource.

**Why.** Every unverifiable dependency found while designing the filter came from the record-level
reading, which requires the filter to assert things about arbitrary data fields whose nesting and
cardinality Usher can neither see nor require. Resource-level needs one single-valued field, and a
positive `in` clause on such a field is an exact match whether the mapping is flat or nested. It
also aligns the enforcement unit with the sharing unit already committed to under FR-08.

**Resource keys are per-catalogue plugin config.** Keys are homologues: one slot filled differently
for each body of data a deployment serves, with Usher never learning any field name. Catalogues
within a single deployment will disagree, since different bodies of data arrive through different
submission services and expose different fields for the same role.

Recorded in `plugin-integration.md` as four checks a plugin must perform on a candidate resource-key
field, because each was found to be a real failure mode rather than a hypothetical: that it is
single-valued; that cardinality is verified against a declaration rather than inferred from an
Elasticsearch mapping, which cannot express it; that its values were observed rather than read off a
display label; and that the term is not overloaded elsewhere in the same deployment.

Also recorded: a submission-level identifier can be a legitimate resource key or a serious mistake,
and the field itself does not reveal which. Legitimate where the submitting body is the governance
unit and values come from a registered vocabulary; wrong where it stands in as a proxy for a property
of the data. The judgement is per-integration.

**What MVP gives up.** A resource holding records of mixed sensitivity must be split into separate
resources. Under OCAP that is arguably correct, since separately governed data gets its own resource
and steward rather than living as a tag inside another resource.

**Deployment specifics moved out.** Catalogue topology, resource-key field names, vocabulary drift,
and submission-service authorization gaps for the first integration now live in that integration's
own repository under `.dev/docs/usher-integration.md`, which links back here. Keeping them in this
repository made one deployment's configuration read as a platform rule.

## Corrections to the zero-entitlement decision

Two changes to `Enforcement` in `.dev/design/decisions.md`:

- **Added an `allow` arm.** A catalogue can be open by configuration and needs an unrestricted
  query; without a named arm the only way to serve it would be emitting the empty match-all
  combination the decision exists to prohibit. Naming it lets the audit trail distinguish
  "unrestricted by configuration" from "unrestricted because the filter evaporated," which are
  identical in an emitted query and opposite in intent. The alternative considered was enumerating
  every open resource into a positive clause, which puts a catalogue's whole resource list in every
  token.
- **Dropped the `revoked` reason as unreachable.** The bridge drops a user's cached token on a
  revocation event, so the next request re-fetches a payload with no grants for that resource,
  which surfaces as `no-grants`.

## Provisional decision: additive rendering over subtractive exclusion

Recorded in `.dev/design/decisions.md`, marked provisional. The plugin would render a resolved
grant set as a union of positive predicates, one branch per grant held, rather than computing
exclusions by subtracting held categories from a category set configured locally in the plugin.

**Scoped to post-MVP, and the encoding question is settled.** Under resource-level enforcement
there are no per-record category predicates, so the filter is a single positive clause and additive
rendering is what it does trivially. The decision governs the post-MVP record-level case.

Two results, both established by executing the SQON compiler rather than reading it:

- **Subset containment is expressible in one clause, but not via the operator whose name suggests
  it.** `not-in` and `some-not-in` emit byte-identical ES on flat fields; on nested fields each
  behaves like the other's name. The single-clause form is `not` of `not-in`, linear in the number
  of grants, and it is documented nowhere.
- **It requires a `nested` mapping.** On a flat field the same expression double-negates to plain
  `in`, existential rather than universal: silently the wrong quantifier, in the permissive
  direction. No `terms_set` exists in the compiler as a fallback. Usher cannot require a mapping
  shape from deployments whose data models it does not know, so record-level tagging is available
  only where a deployment supplies conforming data, verified at plugin startup.

A near-miss worth recording: the published operator table documents `some-not-in` in terms that
describe `not-in` and vice versa, in exactly the nested case where they differ. A design that took
the documented meaning would have emitted an existential predicate where a universal one was
required, returning records the requirement exists to withhold. Both assertions underpinning the
zero-entitlement decision were separately confirmed correct as emitted, and one detail sharpens it:
`in` with an empty value array is the only fail-closed encoding of "entitled to nothing" in the
whole operator set, since negating it inverts to match-all.

Recorded as a standing rule in `plugin-integration.md`: operator semantics on the enforcement path
are established by execution, never from reference documentation. The specific documentation
defects stay tracked on the Arranger side rather than being restated here.

The decision turns on failure direction: in a subtractive model, losing a term widens access; in
an additive model, losing a term narrows it. A failure-mode comparison table accompanies the
decision and is repeated wherever the decision is referenced.

Supporting arguments recorded alongside it:

- Term loss is a demonstrated property of `@overture-stack/sqon`, not a speculative risk. Empty
  combinations validate and compile to match-all, `reduce.ts` prunes empty inner combinations,
  and `removeFilter` converges on an empty combination. Two further hazards are noted as
  unverified: `groupingOptimizer` flattening empty combinations, and `SqonBuilder.not([...])`
  inverting AND/OR when merging same-field exclusions.
- Subtractive rendering routes every decision through `not`, the one operator carrying a flagged
  merge defect. Additive rendering uses `in` for effectively everything.
- Grant computation is already additive across the three tiers, so subtractive rendering inverted
  the result mid-pipeline for no reason.
- Audit answers become local: "why can this person see this record" resolves to a specific grant
  rather than to the absence of a matching exclusion.

Two consequences recorded:

- Membership becomes an explicit positive grant. Subtractive rendering gave untagged records away
  for free since nothing excluded them; additive rendering has no implicit baseline, so membership
  must render to its own predicate. Exact shape is open.
- The grants token carries held grants only. Carrying a resource's full configured category set
  was considered as a way to make subtractive rendering fail closed on config drift; additive
  rendering does not need it.

## Decision: zero entitlement is a distinct state, never an empty filter

Recorded in `.dev/design/decisions.md`. The bridge returns a discriminated `Enforcement` result
(`deny` with a reason, or `narrow` with a non-empty SQON) rather than a bare filter value.

This adds no new rule. `plugin-integration.md` already required denial to be rejected before
filter construction. What was missing was a mechanism making it unskippable: given a bare
`SqonNode`, the natural plugin code has no branch to forget because it has no branch.

Verified against `@overture-stack/sqon` while establishing this:

- `SqonCombinationSchema` declares `content: zod.array(SqonSchema)` with no minimum length, while
  every leaf schema constrains its own content. So `{ op: 'and', content: [] }` validates.
- `SqonBuilder.empty()` produces that value and three tests assert it. Every builder chain starts
  from it, so it is the identity element rather than an edge case.
- A clause-less `bool` is match-all in Elasticsearch for any combination operator, so an empty
  `or` is match-all too rather than match-none.
- `in` with an empty value array validates and compiles to match-none, since
  `SqonScalarOrArrayValueSchema` has no minimum length unlike `all` and `wildcard`. An accidental
  deny encoding sitting one nesting level from its exact inverse; explicitly not used.

`deny` asserts only "do not query the data layer" and carries no status code, since the
existence-denial invariant makes an empty result set likely more appropriate than a 403 for search
endpoints. The `reason` field serves the audit trail rather than control flow.

## JWE rationale rewritten

The recorded rationale for JWE over JWS assumed the user receives and forwards the grants token.
That premise does not hold: the bridge is a library in a client data service and obtains the token
from the controller itself, so it never transits the user agent. The decision stands on two
rationales that are independent of the user being in the path:

- Audience separation becomes cryptographic and fails closed. A payload issued for the wrong
  application fails to decrypt rather than leaking.
- Grant sets stay out of incidental disclosure surfaces such as logs, error reports, and traces.

The superseded premise is kept in the record rather than deleted. Key distribution cost is smaller
than it first appears: both candidate key-wrap algorithms are asymmetric, so per-application
audience scoping requires public-key registration rather than secret distribution.

## Bridge query-language boundary corrected

`architecture.md` barred the bridge from any knowledge of a query language. Too broad: SQON is a
shared Overture language rather than one adopter's dialect, since Lyric consumes it as well and
Arranger merely owns the module. The prohibition now covers the backend instead. Rendering a
resolved grant set into SQON is generic and may live in the bridge; compiling SQON into
Elasticsearch DSL or SQL is adopter-specific and belongs in the plugin.
