# 2026-09-18

## The source model was read, and it inverted the reading built on it

RABAC's second stage only removes. `avail_session_perms` is "the maximum permission set available in
a session", filters are applied to each permission in it, a permission returning FALSE is blocked and
removed, and the profile states there should be no filtering policy that evaluates to permit. Two
filters on one object combine deny-override. The corpus had described Usher's grants as the same
two-stage structure and they run the opposite way: a grant adds and grants combine by union.

Underneath that, `PRMS = 2(OPS x OBS)`, so a NIST RBAC permission already names its object and a role
hands out verb-object pairs. That is why role explosion happens. Usher's ceiling carries verbs only
and every object arrives through a grant, so its first stage is weaker than RABAC's and its second
does constructive work RABAC's never does.

**Reconciled by reading the ceiling as universal.** A role's capability is held over every
`(resource, category)` pair that exists and the grant set names the pairs to keep. Union of kept
pairs is still subtraction from a maximum, so nothing about the additive implementation changes and
four behaviours stop being separate stipulations: no grants reaches nothing, a resource with no
categories reaches nobody, an empty category satisfies nothing, and a category can only restrict. The
invariant is `effective ⊆ ceiling`, asserted at issuance rather than documented.

**Two questions the paper settled.** The ceiling is a real gate, because the filter can never add.
And it is global to the principal rather than per resource, because `avail_session_perms` never
consults an object.

**Three things it does not have**, so none can be checked against it: groups, acceptance, and an
administrative model. The paper faults earlier work for the third and its own story is that filter
policies live in a separate file.

Two claims in `rabac-alignment.md` misdescribed the paper and were corrected: that it states directly
that operations carry different constraints, which is a consequence of the typing and the example
rather than a sentence, and that it has session attributes, which it explicitly declines.

## Categories select records, and the reversal reached six files

A category is a condition a record carries, not a clearance the whole resource requires. The
enforcement clause pairs the resource's field value with the category's, one clause per grant,
composed with `or`. A resource of mixed sensitivity serves each principal the records their
categories reach.

Reversing it reopened a question parked as superseded: whether the access-level value attaches per
record or to a submission-shaped parent, and at what nesting depth, which `plugin-integration.md`
itself calls design-invalidating.

**The category-to-field mapping check moved from post-MVP to load-bearing.** Two documents said a
plugin needs no category mapping and has nothing to check. It needs one to render any clause, and the
startup reconciliation against Usher's dictionary is what stops an unmapped category being served as
open.

**The real limit is the data rather than the query language.** Access is decided from descriptions
the data already carries and nothing is written into it to make a decision possible. Both catalogues
of the first deployment have been read and neither carries an access-level field, so the category
clause has nothing to test there and the emitted filter is the resource clause alone.

## Acceptance, and what it settles

What a person accepts is the outcome stated per category, not membership of anything: in this
resource, on this category, these capabilities. A granter and a grantee decide different things, so
the grant records one and an append-only decision row records the other.

Four consequences. A group grant does not bypass acceptance. The grant and the decisions cannot
contradict, because a record of a decision is not a copy of the thing decided. The capabilities on
the row are a snapshot of what the member was shown, never a cache. And divergence has a safe rule:
keep what was accepted intersected with what the role now confers, so narrowing is silent and
widening asks.

`open` needs no acceptance: an anonymous request has nobody to accept, and a registration-gated
`open` is accepted with the platform's terms.

**The decision time is a UTC instant rather than a date**, because selecting the latest decision
needs a total ordering and two answers can land in the same minute.

## The model was rebuilt on groups, and groups are not in the first release

The schema was rewritten so that roles and grants are held only by groups. The user flows never
mention a group in eleven pages, the requirements never mention one, and `phase-1.md` lists user
groups as a v2 stub alongside field-level restrictions and multi-tenancy. Every share in the flows
names an individual by email and a steward's dashboard lists people.

The correction restored the per-person shape and kept acceptance. Removing the group design
afterwards was a second error: with no group holding a role, nothing held a role per resource, so the
ceiling was rewritten as global, which is coherent alone and incompatible with groups. Restoring them
required putting the resource back. **A known-future item stays in the design because its shape
constrains the present one**, recorded as a decision.

**Settled shape.** One `grants` table carrying resource, category, holder and role, with a holder
that is a user or a group. No separate role assignment: being trusted as a curator is a decision
about a resource and a category rather than a standing property of a person. `grant_decisions` is
append-only and serves both holders. Group holders are designed and unused in the first release,
which costs no migration because the holder column already accepts them.

## The platform envelope

CloudEvents `specversion` 1.0, verified against the specification rather than recalled. `time`
required here though optional there, narrowed twice: UTC with `Z`, since RFC 3339 permits an offset
and a corpus of mixed offsets cannot be ordered, and seconds always present. `type` as
`bio.overture.<entity>.<act>`, organization prefix and no service segment, because `source` already
says which service emitted and what distinguishes two denials is the entity. `dataschema` optional.
One `source` per deployment, never per replica, because `source` plus `id` is the deduplication key
and a source may span producers.

`actorId` carries the `sub` claim, always server-derived. A neighbouring field elsewhere on the
platform is client-supplied and persisted, so the two have opposite trust properties and the mistake
a shared name invites is reading a caller-asserted value as an audit identity.

`actorType` gained two values rather than one. Anonymous, and system, which was already absent: the
schema documented `actorId` as null for automated events while offering only `human` and
`serviceAccount`.

**Two items owed by the platform**: a `source` convention, since an undisciplined source weakens
deduplication whatever `type` looks like, and a shared entity vocabulary, which only the flat type
form requires.

## Corrections from peers, and the pattern behind them

Three constraints offered by a consuming application described how it works today rather than what a
published interface must support: a client-side session check framed as a browser-only architecture,
a styling system already being migrated away from, and an unmerged pull request described as a
package the platform has. Each was caught, none by this side. The practice that follows is to label
an integration fact as current implementation or durable requirement when it is offered.

A fourth was ours: our own documents said one portal is client-only by design and cannot host a
bridge. It is the same framework and simply not configured to, so the gap is setup rather than
architecture and the work carries across.

## Checker defects, three of one kind

An exclusion anchored on a line number stopped excluding when an edit pushed the text to a new line,
and the file stating the rule began failing it. The pattern count in the summary was maintained by
hand and read 13 while the file held 12. And a construction that leaves the reader to fetch a verb
phrase from an earlier clause passed every pattern, found by a reader rather than by the tool. All
three are now fixed, the count derived rather than written.
