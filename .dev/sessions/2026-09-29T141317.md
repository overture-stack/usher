# 2026-09-29

## The build order runs consumer first, from the adapter to the controller

The Arranger adapter is tested and built first, in the Arranger repository, with the bridge and the
controller mocked. The bridge follows in this repository with the controller mocked, and is then
tested together with the adapter. The controller comes third, tested for whatever the bridge's tests
do not already cover, and integration tests across the bridge and the controller follow without
Arranger's adapter. Keycloak and Stage are integrated when a step needs them rather than first, and
the adapter imports the bridge through `npm link` during development, so the bridge package exists
with its types from the first step. phase-1.md's build order and its rules for the mocks are
rewritten to match: the consumer's tests decide an interface's shape and the case table decides its
answers, the controller mock issues real tokens, and it is stopped during the bridge step to exercise
the grace period.

**Step 1 is split by concern.** The adapter's tests and the shared types they import are written
from Usher's side, since the queries and responses are as much Usher's concern as Arranger's, and
Arranger's side reviews them until they are ready to code against; the enforcement itself is then
implemented from Arranger's side. The controller lives in `apps/controller` as the private package
`@overture-stack/usher-controller`, beside the bridge in `modules/express-bridge` and
`@overture-stack/usher-types` in `modules/types`, holding the payload and enforcement-result types
and their validators, which the bridge re-exports. It is the first package created, since the
adapter's tests import it. The toolchain is settled together with Arranger's side.

## The toolchain takes each tool at its latest, and the shared types wait for Arranger

This repository uses pnpm, Node 24, TypeScript and zod at their latest (7.0.2 and 4.6.5 on this
date), tsdown for builds, pinned exactly below 1.0 because tsup is no longer maintained,
`node:test` run through `tsx`, and jose for the encrypted token, recorded in the technology stack
note with the date the versions were checked. Arranger's side is on TypeScript 5.8 and plans the
same upgrades, so `@overture-stack/usher-types` is not created until Arranger can read what it
publishes, and it is not published until it is ready: local development links it, a commit made
while linked leaves the link out of the committed lockfile or workspace file, and Arranger's CI runs
the adapter's tests only once the package resolves from the registry. Data filtering comes before
logging: the adapter's logging tests are written with the rest, and the logic follows once filtering
works. The prose check's dash pattern now also catches a double dash ending a wrapped line, found in
the technology stack note.
