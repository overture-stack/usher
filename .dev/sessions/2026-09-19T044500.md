# 2026-09-19

## The first integration target is Stage, not the iMS portal

Stage is where enforcement gets proven, in overture-dev, with the learnings carried to iMS
afterwards. The iMS UAC user flows still define the behaviour Usher must support, and they describe
portal-ui rather than Stage, so the two are different lists: the flows are the requirement and Stage
is the proving ground.

This reorders the critical path. Notification, the "Shared with Me" surface and the sharing interface
are all portal-ui's and arrive with iMS. What Stage-first needs is the enforcement chain end to end,
and a way for grants to exist without a management interface, which the build order answers by
mocking them.

**Stage runs a real server side already**: three API routes, server-side token exchange, and an
httpOnly cookie encrypted with a server-only secret. A bridge sits inside a trust boundary that
exists rather than needing one built. Stage has no study management UI; its whole application is four
pages and a two-item user menu.

## The management surface ships as a package

Usher ships it and portals mount it, rather than each portal building its own. The iMS surface is the
input for most of it, and one part is not a port: that surface grants access as a flat list of
holders on a resource, its classification field is chosen once at creation, and it contains no
category-style scoping at all. So per-category granting is new on both sides, since no data in the
first deployment carries a distinguishing field and no management surface anywhere grants one.

**Two guarantees in two places.** Usher's read owns what the data contains, so nothing downstream can
render what a principal lacks. The package owns what the rendering implies, which can leak while
every value is correct: a count with a denominator, an affordance for the unreachable, an empty state
separating nothing-here from nothing-for-you.

**The package renders and does not fetch.** A fetching package would need a server in every host
before any host could use it; one that renders from injected data works in both. The read shape is
therefore the package's input type, which makes specifying the component's props the way to specify
the contract.

**Five constraints from the consuming side.** Theming through CSS custom properties rather than a
theme object, because that is the one input both the current and the migrated stack can supply and
the package ships before the host migrates. No hardcoded vocabulary. Injectable data. Components
rather than routes. And no store of its own.

**One input for obtaining data, used by every path including internal bootstrap reads.** Taken from a
failure next door: a host routes an injected fetcher through its own proxy, and one bootstrap call
assumes the fetcher uses the URL it is handed, composing into a doubly-prefixed 404 that appears only
in the host's environment and never in the package's tests.

**CSS delivery is an interface decision.** Host imports a stylesheet or the package injects one,
never both, and nothing internal assumes a path only the package's build resolves.

## The build order, and why it runs backwards

Keycloak configured so a person can sign in, then a barebones controller with mocked grants, then the
plugin and bridge against it, then comparing signed-in against anonymous in the portal, then the
profile surface and the rest of Keycloak, then the real controller, then the management UI and
submission pieces in parallel.

The contract is defined by the thing that consumes it. Five things asked of the mock: seed it from
the case table rather than from what the plugin asks for, do not let it be accommodating, issue real
tokens, stop it at step 2 to exercise the bridge raising, and wire it to the conformance corpus so it
outlives step 5. The portal comparison covers counts as well as rows, because counts are where
existence leaks and where the search layer's depth-2 defect lives, and it needs one synthetic
catalogue carrying a category field or per-category enforcement reaches production unexercised.

## Four blockers closed

**JWE algorithm.** `dir` with A256GCM, symmetric, one key per controller-and-application pair held in
the secrets store and injected into both pods. Per application is the load-bearing part: a shared key
would make `aud` a string comparison rather than a boundary. Symmetric because the deployment already
distributes secrets, so asymmetry solves a provisioning problem that does not exist here. What is
given up is that a minted token produces no exchange event, accepted because the audit trail is a
detection surface rather than evidence against a compromised ushered application, and because such an
application can read its own store without any token. This reverses an earlier resolution that had
corrected the corpus toward asymmetric.

**Payload versioning.** Negotiated at the exchange, never tolerated at read time. The bridge sends
the set of versions it supports, the controller emits the highest in the intersection or refuses.
Read-time tolerance is unsafe here specifically because an added field can narrow: a future
withholding marker would be silently ignored by an older bridge. The direction is asymmetric, a newer
bridge with an older controller being benign. The first release has one schema and the handshake is
built anyway, because adding it later is a coordinated change at both ends.

**Write versus read access.** Closed by scope: resource creation at submission time is not in the
first release, so nothing couples submission to read. It fits later without a schema change, since
`resources` already carries `created_by`.

**The last-policy-change timestamp.** Closed by replacement. The marker was per principal while the
dangerous change is per resource, which is why its write list could not be enumerated: adding a
category to a resource moves nothing on any principal's rows while removing their access. Replaced by
the computed payload in the shared cache, deleted by anything altering what a principal holds, and a
category version on `resources` bumped by any `resource_categories` write and compared on refresh.
Each marker sits next to what changes it, so there is no fan-out to compute.

Reissue is not renewal: the cache saves the computation and never the expiry, so the earliest grant
expiry is cached alongside the payload and bounds every reissue. The asymmetry is correct, with
revocations immediate and new grants lagging by up to one TTL.

**Recorded as the frame**: this is the access-and-refresh-token shape rather than a new one. The
Usher token is the access token, the exchange is the refresh, the fast path is introspection with a
cache, and anything proposed without a counterpart in that shape is worth a second look.

With three of its dependencies closed, the database schema is waiting on nothing and is the only
design work left before implementation.

## Event vocabulary

`revocation.modeChange` became `revocationChannel.modeChange`: `revocation` was already an act in
`grant.revocation` and `identity.revocation`, so one word did both jobs. **No word is both an entity
and an act** is recorded as the first concrete constraint on the shared entity vocabulary the
platform owes. It was the only collision.

The event's own description listed three modes where there are two. Suspension is what happens to
cached tokens inside revocation-uncertain mode, not a state of the channel.

**Alerting happens through recording.** Usher holds no rules and sends no notifications; it emits
events and severity routes them. Conditions only Usher can see become event types, and four already
exist. The general case is silence: a channel that stops carries nothing to match, so only the
component expecting the events can report that none came.

## The capability vocabulary, settled

A capability is `entity.action`, written in full and displayed as the action alone. The entity
decides the plane, not the action: `record.create` is data plane and `resource.create` is control
plane, and both are "create". That is why `plane` sits on `entities` rather than on each capability,
and why every entity sits wholly in one plane.

Data plane, four entities, of which the first release builds `record` and `artifact`:

    record     create, read, update, delete, export, aggregate
    field      read, update, export, aggregate
    revision   read, export
    artifact   create, read, update, delete, export

`export` rather than `download`, and it is not a copy control: bulk egress is a different act from
reading one record, and it warrants its own event and approval. `aggregate` is contributing to a
count without being individually readable, which is the discovery tier the model previously could
not say. Archiving, publishing and suppressing all collapse into `update`, since each sets a value on
a record that continues to exist.

`field` is an entity, and the argument that kept it out was wrong three times. Each of `artifact`,
`revision` and `field` was first rejected on the grounds that holding its capability without
`record.read` means nothing. That test is invalid, since capabilities are independent and roles are
what prevent nonsense pairings. The valid one is whether the thing is separately addressable and
carries actions the others do not.

## The token nests, and the schema gained two columns and lost one

    "HEART_STUDY": {
      "open":       { "record": ["read"], "revision": ["read"],
                      "field": { "basic": ["read"], "clinician": ["read", "aggregate"] } },
      "controlled": { "record": ["read", "delete"] }
    }

Resource, then category, then entity, then actions, with `field` mapping to its own categories first
because a field is the one entity a record category further partitions. That expresses what no
flatter shape could: clinician fields readable in open records and not in controlled ones.

The outer value stopped being a list whose every element carried one key. Bare action names stopped
working the moment a second data-plane entity existed, since `read` no longer says whether it is
`record.read` or `field.read`.

`grants` carries `record_category_id` and `field_category_id`, each naming an axis rather than a type,
so the same category may sit in either. Exactly two columns, and the count is derivable: categories
partition the two data-plane entities that carry them, while a revision inherits its record's and an
artifact's reach comes from provenance.

**`categories.kind` was added and then removed, and the removal is the better answer.** What a
category selects is decided by the plugin's mapping, two plugins could map one name differently, and
Usher can neither know nor verify either. A column here would have been Usher asserting a fact it
does not own. Which column of a grant a category sits in says the same thing without the claim.

`basic` is the field residual, granted rather than assumed, exactly as `open` is on the row axis. A
grant naming `clinician` and not `basic` reaches the clinician columns and hides the rest, which is
the de-identification case. A missing `field` key is the absence of a partition rather than the
absence of a grant, which is the one place absence does not mean nothing, and keeping the two
distinct preserves the signal a plugin uses to decide whether to prune columns at all.

## Field restriction is a contract change, not a configuration one

Established against the first integration rather than inferred. An enforcement hook returns a filter,
a filter selects records, and which fields come back is a projection. A predicate and a projection
are different things and the seam carries only the first. So field restriction needs a second return
channel from the bridge rather than a second mapping behind it, and it is the first thing this design
has asked for that the seam cannot express.

Three properties that generalize past the one integration. A projection on the record path does not
reach the aggregation path, so a restricted column stays enumerable through its facet, which is why
`field.aggregate` is separate from `field.read`. A bulk export path is where the restriction is most
likely to be silently absent, because nothing about it looks like a query. And removing a restricted
field from a generated schema is an oracle where pruning it silently is not, which holds only while
the field is nullable: a generator marking one non-nullable turns a prune into an error and the error
into an oracle.

A store that duplicates a value at write time defeats field restriction from underneath. That joins
cardinality, per-record category marking and cross-catalogue identifier uniqueness as a
data-modelling precondition rather than an enforcement defect.

## An unimplemented capability fails closed only where the action has no path

The standing rule was that a wide vocabulary is safe because an unsupported capability is never
tested. True where a capability permits, false where its absence restricts a path already being
served: the service is answering already, the capability exists to narrow the answer, and a plugin
that does not check it narrows nothing. `record.delete` with no delete path is closed. `field.read`
on a restricted column, unimplemented, serves every column, and that is the severe case.

It is also the strongest argument for the controller retaining what each plugin declared. Without
retention a grant naming a capability its audience lacks is writable and surfaces at query time, and
what happens then depends on clause polarity: a positive clause on a missing field matches nothing
and denies, while a negated one matches nothing, negates to match-all, and permits. `open` renders as
exactly that negation, so non-retention converts an authoring mistake into a silent widening on the
one category every principal holds.

## Keycloak, closed both ways

Not the replacement, and not the host. Two questions had been held as one: adopting Keycloak
Authorization Services, and shipping Usher's own model as a Keycloak extension. The second was never
written down anywhere, which is how it kept returning. The decisive reason is the same for both and
is a commitment already made in three documents: authorization stays independent of the identity
provider. Three more for the extension form: the grants live away from the accounts so that an IdP
owning policy is not a single point of failure for both layers; the revocation channel holds
long-lived connections out to every bridge; and an extension couples Usher's release cadence to
Keycloak's and puts its admin surface inside the console this design exists to keep people out of.

Two things were never tested and are accepted as untested, since neither answer would have changed
the reason: whether Keycloak Authorization Services can emit a residual filter, and whether delegated
non-administrative governance is expressible in it.

## What the consistency pass found

Run against the whole corpus after the above landed. Beyond the expected stale references:

**A hard invariant contradicted a new capability.** "Excluded records do not appear in counts" and
"a discoverable-but-inaccessible mode will not be introduced" sat fifty lines from `record.aggregate`,
which is exactly that mode. Resolved by stating the boundary: excluded means no grant of yours reaches
it, and such a record contributes to nothing. A record reached at `aggregate` and not `read` is not
excluded, it is discoverable because an instance conferred that deliberately.

**The worked example rendered `open` as a concrete predicate**, mapping it to a field value, when
`open` is the residual and has no value of its own. Its setup also gave a resource a category it did
not list. Both corrected, and the example now shows the complement rendering.

**The composition table was the subtractive model** in a document whose neighbouring paragraph says
nothing is subtracted, and its token column used the retired flat shape with an empty list for a
principal holding no grants, which cannot occur while everyone holds the baseline.

**A claim that a grant carries a deferred start** while the schema carries only `granted_at`. Stated
now as a limitation, with the note that adding it later is one nullable column.

**The step table disagreed with the calculation it claimed to mirror**, in both order and tables
consulted. Realigned, and the step numbers are now the calculation's own.

**Two count claims drifted** when `entities` was added: ten tables became eleven, and the kind table
was missing two rows. Both listings now agree at thirteen, verified by comparing them mechanically.

**The atlas index failed its own integrity check.** It carries a rule saying completeness needs a
count rather than a read, because a file linked only from a roadmap entry becomes unreachable when
that entry is removed. Three files were unlisted, one of them worked on the same day.

**A section reference broken by a rename in this session**, and one predating it. Both repaired, and
every internal link and named section reference now resolves.

**`custodianship.hold` is a permission the grant table already expresses.** A custodian is someone
holding a grant whose role is `custodian`, on one category, with the wildcard in the resource
position. The open question asked whether it is one column, one join table, or two; it is none of
them, and cardinality needs no decision because one grant per category is the ordinary shape.

## Corrected by Arranger

Recorded because the correction was verified rather than argued, and because the placement it
suggested is better than either keeping or dropping the finding.

Saved sets are **not** mutable: creation is the only write path, so the provenance check that refuses
a set drawn from an unconfigured resource runs on every version of a set there is. This session had
recorded the opposite and raised it as a live gap on the first integration. The reasoning survives the
correction, so it is now a precondition on the sets feature, which is the work that would introduce a
second write path. A gap recorded as live gets checked, found absent, and dropped, and the constraint
disappears with it.

The same exchange supplied the reconciliation protocol's starting point: what a plugin can declare,
that catalogue load is the only moment it can run, and that mismatch behaviour should split rather
than follow one rule, since an unmappable category cannot render a clause while a cardinality
divergence that stops working catalogues is its own outage.

## Two more from Arranger, both after the pass

**`field.export` stays separate from `field.read`, for a better reason than the one that suggested
it.** Bulk-against-single was the original argument. The stronger one is a corollary of the
unimplemented-capability rule: folding export into read would make partial implementation unsayable,
so a service pruning columns from records and not from exports would hold grants that read as
restrictions the export path never applies, with nothing in the vocabulary able to state it. A
capability whose absence restricts needs partial implementation to be legible, and the vocabulary is
the only place that legibility can live.

**Its honest limit is recorded beside it.** Granting `field.read` while withholding `field.export` is
not a confidentiality control: anyone who can read a column through ordinary results can page through
and assemble the same extract. What the split gives is rate and auditability. Same overreach the
record-axis `export` already carries a warning about, caught before it could be claimed twice.

**The discovery tier needs a second seam widening, independent of the first.** `aggregate` without
`read` requires the enforcement hook to answer one surface permissively and another not, and the hook
receives no indication of which surface is asking, so one filter serves records, aggregations and set
materialization alike. Projection and resolver identity are two distinct changes at that boundary and
neither implies the other; they are costed separately now rather than as one field-level change. It
does fail closed while unimplemented, since a single filter either permits all three or denies all
three.

## A reader got stuck, and the crux was not the first diagnosis

A non-technical reader read the onboarding's "Datasets and categories" section and could not separate
a dataset from a resource, taking a long conversation to resolve. Worth recording in full, because
nothing mechanical could have found it and the first repair was aimed at the wrong thing.

**The first reading was that the section treated the two asymmetrically**, a dataset "carrying
identifiers" and a category being a "level of sensitivity" the dataset "lists", when the mechanism is
symmetric: both are a field and a value, which is why they compose by pairing and why a grant is two
tests. That reading was correct and it was not the crux. Fixing it improved the section and would not
have unstuck him.

**The crux was that `dataset` read as a reserved term rather than a generic one.** The document bolds
a word on first use to mark a term being defined, and does so correctly for `enforcement`, `instance`
and `policy`. Then it bolded `dataset`, which is not a term at all. He had learned the convention
correctly, and being right about it is what made him wrong about the word. The document already had
the remedy and had applied it once, disclosing that it says "person" for what the model calls a
principal, and simply never said the same about `dataset`.

**Adding the disclosure early was still not enough**, which is the part worth keeping. The next
paragraph went on to define the entire mechanism in terms of the stand-in, so the document contradicted
its own disclosure within three sentences. Definitions belong on the word the system uses; the
stand-in is a pronoun and can only be used once its referent exists. The section is now titled
"Resources and categories" and says `resource` throughout, all forty-five occurrences, and the rest of
the document keeps `dataset` because the term has by then been established.

**A second misreading rode along with the first and is the more expensive one.** Having taken the
stand-in as a term, he read categories as subdivisions a dataset owns, which is the natural reading
of "a dataset lists the categories it carries". Categories are defined once for the instance and each
resource declares which apply. That containment reading survives contact with everything in the
document except custodianship, which is only coherent because one category is one thing across every
resource. He would have failed later, and a long way from the cause.

Recorded as class O in [doc-review-patterns.md](../docs/atlas/roadmap/doc-review-patterns.md), with
the two-pass check it implies: list every word bolded on first use and ask whether the model has it,
then read only the passages that define, name a structure or state a rule and confirm each uses the
term. The first pass finds the words and the second finds where they do damage.

## The fifteen classes, run across the whole corpus

**Two found something, and both are fidelity classes.** Class D, scope stated narrower than the
system, and class H, ordering by institutional rank. Every resolvability class came back clean except
one instance of B. That is the reverse of the original review, and it is what a week of reading these
documents for resolvability and none for fidelity would predict.

**Class D, three instances, all the same narrowing.** `docs/concepts.md` opened a section with "Usher
controls who can see data", `docs/intro.md` described the permissions model as "what each person can
see", and, more seriously, stated the fail-safe principle as "if a system cannot determine what a
user is permitted to see, the correct response is to show nothing". Usher governs creation, change
and removal as well as reading, and refusing an uncertain write matters at least as much as showing
no records. The same narrowing had already been caught once in conversation and corrected in one
place while three others stood.

**Class H, one instance, with an in-corpus precedent it did not follow.** `admin-model.md` listed
Admin, Custodian, Owner, which frames community custodianship as a subordinate case of platform
administration. `permissions-model.md` orders the same three by widening scope and states why: a
reader meets the narrowest first, and central control is not where the model starts. Reordered to
match and the reasoning cited rather than repeated.

**Class B, one instance out of 184 candidates.** In `docs/concepts.md`, "This is intentional" sat
after a sentence about how suspension differs from Visa expiry, while the sentence following it
argued from the suspension itself, three sentences back. A reader binds the demonstrative to the
nearest clause, which was the wrong one. The referent is now named.

## A probe that could not have worked, and a check that should not ship

**The first pass over the design corpus returned zero on every class, and the probes were the
reason.** They were line-anchored, and this corpus hard-wraps, so a sentence beginning mid-line could
not match. `check-prose.sh` had already solved exactly this and says so in its own comments. Re-run
against flattened text, the same probes returned 186 candidates. **A clean result from a probe that
cannot match is indistinguishable from a clean corpus**, which is the failure the script's own
summary line warns about, arrived at from the other direction.

**Class B was then mechanized, tested, and removed.** The greppable shape is a demonstrative followed
by a bare adjective rather than a noun, since a noun names the referent and resolves it. That matched
six times across the corpus and exactly one was a defect. Whether a referent is ambiguous depends on
the preceding sentence offering more than one candidate, and no pattern can see that. Five false
alarms per run teaches people to skip the output, so the check came back out and the boundary is
recorded in the script: the class is a reading one and stays that way.

## Role seeding, the parts that were only in conversation

Three decisions had been made and not written down, which a check of the corpus against the
conversation found rather than memory.

**`grant.createSelf` is folded into `grant.create`.** Writing a grant that names yourself is writing
a grant, and the decision that granting is one function already says the gate applies identically
whoever started the request. What actually differs is not a capability: the self-grant endpoint
requires a TTL and sets the flag producing `grant.selfCreation` in the audit trail. Both survive the
fold, and the endpoint rule now reads as applying to anyone holding `grant.create` rather than to
administrators alone.

**An owner may therefore self-grant on their own resource**, and that is intended rather than
incidental. It is recorded, visible and revocable like any grant, and where a category carries a
custodian the custodian is still the last gate. I had flagged this as a question needing an answer
and it did not: "it applies identically whether an administrator, an owner or a custodian started the
request" was already written.

**The control plane seeds `owner` and `admin` and nothing else**, as a matrix, sparse because a
control-plane capability is held or not and there is no progression to run along. An owner is an
admin bounded to one resource: the difference is exactly the four platform-wide capabilities, and
nothing an owner holds is withheld from an admin. Neither carries a data-plane capability, which is
the plane split expressed as seeding.

**`custodian` is unseeded and undefined**, recorded as a decision rather than left as an omission,
because seeding `custodianship.assign` into `admin` is the act that would open the self-appointment
hole. Leaving it out closes that for now without pretending the hole is solved.
