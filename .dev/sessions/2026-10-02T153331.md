# 2026-10-02

## The bridge's filters follow producer rules stricter than what applications accept

decisions.md gains "The bridge's filters carry no empty group, no empty exclusion and no pivot".
Holding zero grants is a deny before any filter is built, whether the grants are all in other
catalogues, every category is unmapped, or a narrowing's predicates fall away. A list that could not
be loaded is a deny. A set is one leaf's value list, and nothing pivots until pivoted groups have
conformance cases. The bridge checks its own output with the `usher-types` validator, and the
application's guard checks it again. `unmarked` renders as a `not` around an `in`, never as a
`not-in`, because on a nested field a `not-in` drops records with no category entries. The rules are
stricter than what an application accepts on purpose: an application keeps honouring the shapes
existing deployments send, and the strictness sits on the side Usher writes.

## The adapter applies an enforcement result, and never receives the payload

adapter-integration.md, architecture.md, the glossary, security-workflow.md, the threat model's
injection gap, the roadmap's adapter entries, the adapter decision in decisions.md and the published
concepts page said the bridge hands the adapter a `PermissionsPayload` to translate. They now match
the decided interface: the adapter supplies the
field names its mapping uses, and the bridge renders one enforcement result per catalogue, which the
adapter applies at its application's hook. The adapter's public surface is recorded with it. The
bridge is passed in, and the adapter depends only on `@overture-stack/usher-types`. The host mounts
the bridge's middleware, which sets each request's results on the request context under one field,
whose name is still being settled. A catalogue with no mapping is a startup error. A configured
catalogue missing from a request's results is a deny. Results missing altogether mean the middleware
never ran, so the adapter throws and logs an error-level event. The bridge answers 503 itself past
its grace period. The open-tier signal describes the principal, never whether anything was withheld
from a result.

## A denial is named at catalogue level, and never at record level

A new decision maps each deny reason to one fixed message: `no-grants` to "You have no access to
this catalogue.", and `unknown-resource` to the configuration-problem text. Never-held and withdrawn
access give the same text, and the distinction stays in the audit trail through `grant.revocation`.
Naming a denial is safe only while every catalogue is listed to every principal; if listings become
per principal, a hidden catalogue's deny answers as a nonexistent one does, and a test is to pin
that coupling now. Partial access carries no message and no count, and any notice is unconditional. The
`reason` field's description in the no-grants decision now says it labels the audit event and
selects the message, rather than claiming three audit events from two reasons.

## Two conformance cases gate controlled data

The roadmap's per-endpoint conformance entry now makes two cases a go-live condition on every
endpoint that returns data: the under-privileged principal against the fully-privileged one, and
parity, where a principal holding every grant sees exactly what the instance returns with access
control off. Parity's one deliberate exception is a record whose resource value is not configured,
so its precondition is listing the resource values in the data against the configuration first.
phase-1.md's table of discriminating pairs gains the parity row.

## The step 1 test plan is drafted

The adapter's tests are planned in Arranger's repository, beside the adapter's design, for review
from both sides. The adapter's fixtures are enforcement results rather than payloads, each traced to
a case, so the same rows become the bridge's expected outputs in step 2. The fake bridge holds fixed
answers and refuses anything else, and its stopped mode answers 503. The router-level suites run on
both engines and include the parity and per-endpoint cases. The log tests are written now and
committed with the logic that makes them pass. Two answers on record disagree about a category the
adapter's mapping leaves out: decisions.md fails startup, and the reconciliation protocol under
discussion takes the resources carrying it out of the catalogue. Both fail closed, so the plan
leaves that one row to whichever is settled.

After review the plan targets the search-server image, which passes each catalogue its own callback
so a callback never learns its catalogue from the request. The GraphQL router exposes the mapping it
resolved, the adapter verifies each catalogue against it before serving, and an unverified
catalogue's callback throws. The GraphQL router carries the request's context to the callback on
every read path without naming any Usher field, so Arranger still runs unchanged without Usher, and
the callback emits one log event per application of a result.

## Stale entries corrected

The token calculation's roadmap entry listed four blocking questions; the ceiling's scope, what RABAC
defines for assignment, and acceptance under a group grant are settled in token-calculation.md, so
three remain, each blocking part of the calculation. The schema entry's blockers have gone: the

## The unit of access is the record, never an item nested inside it

decisions.md now states what the single-valued precondition on the access fields means: a record is
admitted or withheld whole, and its nested items come with it, in its hits and in what its facets
count. Data whose access varies among one record's nested items needs a record per unit of access,
decided when it is indexed, and until a nested shape is decided the adapter refuses to enforce on a
nested field at startup. A facet counting a nested item inside an admitted record is therefore the
designed behaviour rather than a leak.

## The aggregation requirement is settled at any depth

The roadmap's conformance entry had settled the aggregation-path requirement by the filter's shape: a
single clause on a flat field. It now rests on a stronger reason. The search application's nested
aggregation mechanisms read only the client's filter, and the enforcement filter reaches facets
through the composed query alone, which compiles with correct nesting at any depth. phase-1.md's
acceptance test keeps comparing counts as well as rows, without the claim that those mechanisms are a
leak path.

## A category the adapter leaves unmapped withholds its resources

decisions.md now gives each category one of three states per catalogue: mapped, declared absent, or
neither. A category in neither state takes the resources carrying it out of that catalogue and logs an
error-level startup event naming the catalogue and the category, rather than stopping startup, so one
catalogue's gap never takes down the others. adapter-integration.md, permissions-model.md and
to-discuss.md follow it.
