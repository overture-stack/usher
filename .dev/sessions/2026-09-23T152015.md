# 2026-09-23

## `read` is a capability group, `count` counts only, and aggregation is not a capability

`read` names a group: `count`, `view` and `export` on records and fields, `view` and `export` on
revisions and artifacts, `view` alone on the control plane. It is expanded when a role is written, so
no token carries it and no plugin tests for it. Expanding at writing rather than at issuance is what
stops a group gaining a member from widening every role that names it without anyone acting.

`aggregate` became `count` and was narrowed to counts. Anything returning a value or a record needs
`view`, so `min`, `max`, `top_hits` and a terms bucket's key all need it, and a bucket with its count
needs both. Of the three options, only this one makes the name true: `count` meaning every
aggregation would mislead, and keeping `aggregate` on fields would give one concept two names.

The decision is in decisions.md, after the CRUD vocabulary entry, which now records that `view` came
back. The vocabulary, the seeded matrix, the token examples, the payload type, the glossary and all
28 fixtures carry the new names. The type compiles under `--strict` and rejects both old names.
Control-plane `read` became `view` as well, since a capability id and a group sharing one string is
the collision the rename removes.

Three things follow from it:

- A restricted column's facet now closes through `field.view`, because a bucket's key is a value.
  `field.count` against `field.view` expresses the two partial pairings instead.
- Enforcement has to check what a request selects, not only which surface is asking, or a
  count-only principal is served the extremes of a field once the discovery tier ships.
- A principal holding `count` alone sees totals and no facets. Serving such a principal is research, recorded in the
  roadmap, with the three routes any rule has to survive: subtraction, filtering, and repetition. Not live in phase 1, where count-without-view is denied
  everywhere.

The check runs on what a request selects rather than on which aggregation it names, since a bucket
carries a key beside its count and one statistics object carries a count beside a minimum. The rule
behind the classification: a count is safe when the principal already knew the boundaries, so ranges
the principal supplies need `count` and a histogram's buckets need `view`. That holds per response
only, because ranges one unit wide rebuild a histogram. Arranger's field selection already carries
this granularity for what a result returns. It does not decide what a result is computed over: a
principal viewing open records and counting controlled ones needs two sets in one response, and
Arranger resolves one filter per request, so the discovery tier's main case needs the hook evaluated
once per capability, a third widening.

`check-fixtures.py` rejects `read` as an action with its own message. `check-prose.sh` reports the
retired ids and actions, with five cases in the fixture.

A field-role example in permissions-model.md showed one action while the role it named carried two;
it now shows both.

The CRUD decision's table of what each role carries predates the seeded matrix and disagrees with it
on `submitter` and `owner`. Left as found, since it is the historical record of that decision.

## Facet, bucket and count are defined

A facet is a filterable field used as a filter, a bucket is one of its values, a bucket's key is the
field value naming it, and its count is the number of records holding that value. The glossary has
an entry for each. "Value" is kept for what a field holds, so a bucket's count is never called its
value, and the onboarding document now says S3 buckets where it means storage.

## A count-only principal's page has no table, and configuration cannot yet say so

Such a principal gets a headline count narrowed by the facets they may use, so the table is omitted
rather than emptied. The first integration's configuration cannot say a component is not rendered
for a principal, for the table or any other component, and a design for it is wanted within phase 1.
Recorded in the rendering item. The per-type `createState` switch is schema-level and shared by every principal, so it
cannot carry this. And the components turn a withheld configuration into an empty one, so omitting
at the server alone renders an empty panel, which discloses; the component library needs a contract
for absence.

Future scope gained the surveyor who views a bounded number of records: `view` without `count` or

## The reconciliation check runs per catalogue, with three states per category

A category means the same thing across an instance, and each catalogue's plugin decides how to
recognize it in its own data. One study in two catalogues can be `controlled` in one and `open` in
the other, which needs each category to be mapped, declared absent, or not mapped, per catalogue.
Without the declared-absent state, the catalogue with nothing to map takes out the whole study, and
the check cannot tell a deliberate absence from a forgotten mapping. A declared absence is the one
state that fails open when data falsifies it, so a category is mapped wherever a field could carry
it, absence is declared only where none could, and a falsified absence is an incident. The check
that catches it has to run on a mapping change, and Arranger has no mapping-change signal. Recorded
in the reconciliation item.

## The enforcement component is an adapter, and the identity-provider side a connector

An Usher plugin reads as something that extends Usher itself, which nothing does yet, so the
application-side component is an adapter everywhere in the corpus, and `plugin-integration.md` is
now `adapter-integration.md`. The identity-provider side, which admin-model.md had called an
adapter, is a connector. External senses keep the word: Keycloak's and Fastify's plugins, and every
plugin in api-keys.md, which is the Keycloak API-key plugin throughout.

The bridge ships from this repository as `@overture-stack/usher-express-bridge`, from
`modules/express-bridge`, created when implementation begins, and the Arranger adapter is
`@overture-stack/arranger-usher-adapter`. Prose uses the simple names, the bridge and the Arranger
adapter, since a package and its directory say more than the prose name. Recorded as a decision, in
the glossary with a connector entry, and in the retired list.

The prose checker crashed on the rename, because git still lists a file renamed in the working tree.
It now checks only files that exist, treats a pattern block that crashes as a finding rather than a
pass, and lets the glossary check's findings set the verdict, which they never did.

The onboarding document and the phase 1 open items doc were updated to match. AGENTS.md still says
"per-app plugins" and is left for its owner.

## The token names no catalogue

Which of an application's catalogues hold a resource's records is the adapter's to map, and Usher
stays agnostic of how data is structured, so a token names resources only. Recorded beside the other
things the token never carries in security-workflow.md. How the first adapter maps them is being
worked out with that integration and has a roadmap entry, to be documented for other adapters.

## Values named in configuration reach every principal

The rendering item's phase-1 residue is any surface that names resource values from configuration
rather than from data. A portal page listing resources from another source is one, and Arranger's
`extendedFields[].displayValues` is the other, filed as its own HIGH item: a catalogue that labels its
resource field publishes every resource to every principal. It is independent of the three seam
changes and closes by a deployment rule or by shaping that one field.

## Nothing governs what a surface renders, except in the management package

The principle that an affordance for something unreachable discloses was stated only for the

`meta.authFiltered` in the REST contract already answers the honest consumer's need.
