## Usher is an access control service, not an authorization service

Five uses named Usher or the class it belongs to and became **access control service**:
`decisions.md` three times, `why-usher.md`, `iam-primer.md`. `README.md` and `DEVELOPMENT.md` both
said two things separate Usher from a conventional authorization service, which made it an
unconventional one of those; both now say access control service.

Eleven uses stay, because each names something else: EGO, Keycloak Authorization Services as a
product, ELIXIR AAI, and the class itself inside the alternatives evaluation where the market's name
for it is the point.

`AGENTS.md:32` still calls Usher a standalone ABAC authorization service. Instruction files are the
developer's to edit.

The rule is a row in `terminology-usage.md`'s reserved-words table rather than a retired term, since
the phrase stays correct for other systems.

## `ushered` is the qualifier, and the noun after it varies

`ushered application` was being treated as a fixed compound, so six sentences that had said
"service" were changed to "application" when only the adjective needed changing. All six describe
things that serve requests and now read **ushered service**: the component role in
`architecture.md`, two audit statements in `admin-model.md`, two library placements in `phase-1.md`,
and the bridge holder in `concepts.md`.

Recorded in `terminology-usage.md`: both nouns are valid, neither substitutes for the other, and a
role name extends the term rather than replacing it. An ushered service acting as a data provider is
still an ushered service; `data service`, `requesting application` and `target service` describe what
it is doing in that sentence and stop being descriptions the moment one appears where the thing
itself is being named.

## Naming Usher, the controller, and the plane

Three scopes that a bare "the service" collapses. Usher is controller plus bridge plus plugin. The
controller is the only one a network address reaches, since the other two are libraries inside an
ushered service's own process. The control plane is wider than Usher and holds Keycloak as well.

## `check-prose.sh` class L: two bugs, found by testing it

Class L fired on a line reading "a requirement in an earlier draft of the iMS UAC business
requirements", which is provenance about another document rather than this design hedging about
itself. The pattern now requires the reference to point at this document, or to be a bare "an earlier
draft said".

Testing that change against a synthetic case found the older bug: the pattern was lowercase and the

The lesson generalizes and belongs with the script-versus-knowledge finding: a check that has never
been run against a case it should catch is evidence about the corpus only for the cases it actually
matches.

Tables name the container and the entity that belongs, which `group_users` and `resource_categories`

| ------------------------------- | ----------------------------- |

About 130 uses across 17 files. In prose a user **holds a role in** a resource, since that is what

## What a role entails: the ceiling

The question "what does each role permit" was recorded as open in `permissions-model.md` and had
already been answered in `rabac-alignment.md`. A role sets the ceiling, meaning the acts its holder
could perform on a resource's records; a category grant names which categories they may perform them
on and how much of the ceiling applies to each. A ceiling with no grant under it reaches nothing,
which states deny-by-default as a consequence rather than as an asserted negation.

The open question is now resolved and points at the alignment file. What stays open is which
capabilities each shipped role carries by default, which is seeding rather than modelling.

## Three tables the model needed and did not have

`roles` was `(id, name)`, so nothing recorded the capabilities a role carries, and `capability` was
the only primary entity with no table at all despite an instance being allowed to add to the
vocabulary.

    capabilities           (id, name, plane)
    roles                  (id, name, plane)
    role_capabilities      (role_id, capability_id)

`plane` decides who enforces: the controller checks a control-plane capability on an admin call, a
plugin checks a data-plane one before a query runs.

## camelCase, and where it does not reach

Four classes, recorded in `terminology-usage.md`. Only PostgreSQL identifiers stay snake_case, and
for a correctness reason rather than a stylistic one: unquoted identifiers fold to lowercase, so
`resourceUsers` becomes `resourceusers` unless every reference is quoted forever.

The largest application was the audit event payload. CloudEvents restricts context attribute names to
lowercase alphanumerics, but `data` is ours and is JSON on the wire, so its 28 property names now
match the grants token's `generatedAt` rather than the policy store's columns. The two deliberately
malformed names inside the separator rule are shielded, since a rule that quotes a defect has to keep
quoting it.

`grant.burst` became `grant.rateExceeded`. The proposal was `grant.burstThreshold`, which names the
configured threshold rather than the event: the threshold is a separate open item in the same file.
`rateExceeded` matches the payload it carries, `operationCount` and `windowSeconds`.

One reservation stands. The observation family otherwise names a state of the entity in the first
segment: a resource is orphaned, a grant is unguarded. A grant is not "rate exceeded", so this name
reads as an event about grant activity rather than about a grant.

The onboarding passage also says what the signal does not do. It flags and never blocks, because a
custodian is entitled to issue every one of those grants, and refusing them would be the system

## One audit vocabulary, where there were two

`admin-model.md` carried a complete second audit event schema predating CloudEvents: `timestamp`
against `time`, `event_type` against `type`, `GRANT_CREATED` against `grant.creation`, `outcome`
against `result`, and an `action` field duplicating the type in a third naming scheme. Each schema
held something the other lacked.

Folded into `audit-events.md` before deleting it:

- **`actorType`**, `human` or `serviceAccount`. It earns a place because it is not derivable:

`admin-model.md`'s section is now a pointer. That also removed the half-converted table left there by

Recorded as open in `audit-events.md`: types carry no reverse-DNS prefix where CloudEvents says they

## One concept had two names: access decision

`authorization decision` and `access decision` were the same runtime decision under two names, 29
uses between them. `policy decision` turned out not to be a third name for it: most of those uses
expand the PDP acronym, a borrowed XACML term, and `rabac-alignment.md` carries a genuinely different
sense, a decision that constitutes policy rather than one that evaluates it.

**`access decision` wins on a semantic argument rather than a consistency one.** Being authorized
does not mean reaching anything, only holding permission to. The decision resolved at request time is
therefore about access, and it pairs with enforcement, which is what turns it into a result.

Twelve uses swept. Two stay, both naming another system's framing: Cerbos's own API, and the industry
norm that `concepts.md` contrasts a grants token against.

`authorization` had never been defined anywhere despite being used throughout, which the convention
calls a latent argument. It now has a glossary entry drawing the distinction, and a reserved-words row.

**The two names were hiding a contradiction.** `architecture.md` put access decisions in the
controller; `audit-events.md` put them at the plugin. The policy and enforcement split settles it: the
controller decides, the plugin applies that decision to one request, and what happens at the plugin is
not a decision. Fixed. While one concept has two names, a sentence can assert something of one that is
false of the other and nothing catches it.

## `check-prose.sh` could not see past a line break

Every pattern was line-based while the corpus hard-wraps at 98 characters, so any phrase longer than
a few words was routinely split across two lines and reported as absent. A textbook class L instance
sat in `rabac-alignment.md` while the script called the corpus clean.

The multi-word checks now flatten single newlines to spaces before matching, keeping blank lines so a
match cannot span a paragraph break. The substitution is one character for one character, so offsets
still index the raw text and line numbers survive. Single-token patterns stay as grep, since a dash or
an identifier cannot wrap.

Two defects surfaced immediately, both invisible to every previous run: the class L instance above,
and a superseded-findings note in `phase-1.md` pointing at what the file itself used to record.

Two bugs were introduced and caught while fixing it. Line numbers were first counted in the flattened
text, which gives a paragraph index. Exclusions were first matched against the path only, where the
bash version matched the hit text too, which turned a known false positive back on.

The finding generalizes past this script: a checker written against a corpus that wraps has to be
told the corpus wraps, and it reports clean either way.

## Horizontal scaling: the mechanism holds, two pieces of state do not

Multi-instance propagation is designed in `security-workflow.md`: revocation state lives in
PostgreSQL and travels between controller instances by Valkey pub/sub, so no instance coordinates
with another directly. The threat model carries "horizontal scaling with no shared in-memory state"
as a design property.

Two pieces of state have no home, and both weaken in proportion to how far the platform scaled.

- **The grant rate behind `grant.rateExceeded`**, added earlier in this session without saying where
  it is counted. Per instance, thirty operations across three instances read as ten each and a
  threshold of twenty never fires, so the primary detection signal for a custodian acting at scale
  fails exactly where scale makes the misuse worth detecting. Recommended: derive it from the audit
  table, since the events are written there already and a derived count cannot disagree with the
  trail it summarizes.
- **The per-principal last-policy-change timestamp**, already a recorded blocker. Read as a scaling
  question it is the same question: a copy held per instance is shared state under another name.

Recorded together in `security-workflow.md`, with the general form stated: anything a controller
instance would hold between requests belongs in PostgreSQL or Valkey.

## Capability and permission are two things, not one word for one thing

A capability is a functionality an API offers; a permission is a holder's entitlement to use one.
The glossary had been calling a capability "one named action a holder may perform", which folded
both into the term and is why `permission` kept leaking back in as the countable plural.

| Sense                             | Term           | Where it lives                                |
| --------------------------------- | -------------- | --------------------------------------------- |
| what an API offers                | **capability** | a catalogue, `record.view` and `grant.revoke` |
| a holder's entitlement to use one | **permission** | grants, roles, groups, the token              |

167 sites swept. What stayed is the catalogue sense: the capability vocabulary, what Usher ships and
an instance may add to, and the definition itself. Two over-applications were caught in review, where
"the capability vocabulary" had become "the permission vocabulary" and named the wrong thing.

- `role_capabilities` became `role_permissions (role_id, capability_id)`. The row is the permission;
  the column names the capability it permits.
- `category_grants.capabilities` became `permissions`.
- **Permission takes capability's place in the reading path**, since the atom a grant is built from
  is the entitlement. Capability keeps an entry, redefined as what an API offers.
- The old `Permission` entry, which defined the state of being allowed, folded into the new one as a
  condition: a permission is in effect only while its grant is live.

`capabilities (id, name, plane)` stays in the schema, annotated as a catalogue rather than policy.
Whether an instance declares it in configuration or applications register it with the controller is
open, with configuration recommended: an application's capability set changes when the application is
released, not at runtime, and a release is already a reviewed config change. A registry would also
invert the direction the introspection endpoint already runs, giving two sources of truth for one
vocabulary.

The onboarding page's `Permission` entry carried the old state definition and now carries the
entity, in plain language. Republished.

## The capability dictionary is deferred, so the names are examples

Every capability name across the corpus is an example of the `entity.act` shape rather than a
dictionary entry. What an API offers is discovered by building against it, so the dictionary is
settled when implementation starts. What the design commits to is the shape and the plane split.

That unblocked the four off-convention names, since examples need only be consistent:

| Was                    | Is                   |
| ---------------------- | -------------------- |
| `CREATE_RESOURCE`      | `resource.create`    |
| `ASSOCIATE_CATEGORY`   | `category.associate` |
| `CREATE_RESOURCE_USER` | `role.assign`        |
| `category_custodian`   | `custodianship.hold` |

Twenty-three sites. The last of those was never an act at all, which is why it fitted no convention.

The marker is recorded in three places a reader could arrive from: the glossary entry, the alignment
file's vocabulary section, and the service-account list in `admin-model.md`.

`rabac-alignment.md`'s open item closed. It had said the control-plane vocabulary was listed in the
wrong form, which is not what is open once names are examples.

**Creating access and conferring it are two acts**, which was the surviving question and is now
settled. The invitation flow already demonstrates it: an invitation carries the grants it will create
for someone with no account, so the decision exists before any principal holds it, and binding it to
a Keycloak subject happens later at registration without making a new decision. A person decides; the
system binds.

The reason to keep them apart is a governance control rather than a taxonomy preference. A service
account that can bind a grant to a principal must not thereby be able to decide a new one, and one
capability covering both would give it exactly that. The same split runs through the vocabulary:
defining a role is not assigning one.

## `member` retired as a role name, and roles join the examples

Roles are an instance's governance decision in the same way capabilities are, so `viewer` and `owner`
are examples of the shape rather than a set Usher ships. Recorded in the `Role` entry.

**`member` was wrong for the base role on two counts.** It named belonging rather than an act, and it
implied an owner was not one, when an owner belongs to the resource as much as anybody. Now `viewer`,
27 sites plus a dozen prose repairs.

`reader` was the obvious choice and was rejected: this corpus uses "a reader" around forty times for
whoever is reading the document, and these documents get read aloud for review. `viewer` already
appeared as a role name in two places and carries no second sense.

**Submitter is provenance, not a role**, and the entry says so in its lead. It records who uploaded,
immutably, and never changes. An instance may separately name a group "submitters", which is a group
holding a role, has members, and changes over time. Those are different things and the glossary now
keeps them apart.

**The shape instance governance takes** is recorded in `permissions-model.md`: two groups holding
different roles in one resource, split on the plane boundary, with the people who put data in holding
data-plane permissions and the people who decide who else may reach it holding control-plane ones.
Overlap is free, since a person can hold a role at each plane. No new machinery: `user_groups`,
`resource_groups` and the plane split, arranged.

The sweep also surfaced an inconsistency left earlier in the session. `admin-model.md`'s endpoints had
become `/users` while `architecture.md` still said `/members`. Both are `/users` now.

## Owning a resource carries no access to its data

Three statements said an owner holds viewer-level access, which read as a smuggled role hierarchy in
a model recorded as flat. The sharper problem was that the sentence was false on the model's own
terms: a role is a ceiling and reaches nothing without a category grant for each category, stated 640
lines earlier in the same file, so holding a viewer role would have given an owner nothing anyway.

**Decided: ownership carries no data access.** An owner who reads the records holds a data-plane role
and grants like anyone else, and usually does, because an owner is usually also the submitter. Two
roles held by one person rather than one implying the other.

The reason to keep it that way is that governing without holding becomes a principle rather than an
exception. It is the property a custodian needs to govern a community's data without reading it, and
a model where one role skips the category check and another does not has no principle, only a list.

Where the convenience lives is recorded with it: an instance that wants owners to read what they own
applies that when the owner role is assigned, creating the data-plane role and grants alongside, so
the access appears in the grant record and is revocable on its own.

Sites: `permissions-model.md` twice plus the management-roles table, `admin-model.md`'s participants
table, and the onboarding page. The onboarding claim generalized rather than shrank: it had said a
custodian and an administrator govern without holding, and now says authority over who may read is
never itself permission to read, which is true of all three roles and is the simpler sentence.

`admin-model.md`'s class L instance went in the same pass, reframed as **Rejected: read access as a
property of submission**. Whether submission gives read access stays open, recorded as a blocker in
`phase-1.md`.

## The four tables are two relations, and stay four

Recorded earlier in this session as duplication to resolve. They are not duplicates.

The grant pair cannot be merged: a grant to a person carries a `state` because acceptance is
something a person does, and `permissions-model.md` already records that group grants have no
acceptance step, groups being managed by admins rather than self-selected. Merging would make the
column meaningless for every row in half the table and invite code that reads it without knowing
which half it came from.

The role pair could be merged and is kept parallel instead, so the schema expresses the holder
distinction one way rather than two, and so each table names the entity that belongs rather than a
position.

**That closes the holder question too.** Holder is a position a user, a client or a group occupies,
which is why it belongs in the glossary and not in the schema. The cost of the split is a union
across both tables of a pair, which is already how a principal's own grants combine with their
groups'.

## `holder` restricted to qualified use, and a rule about which way a sentence runs

Bare, the word does not say what is being held, and the corpus had it meaning four different things:
whoever a grant is recorded against, an owner, whoever ends up with a token, and ordinary English.
Qualified, it is fine and stays available: a **grant holder** or a **token holder** names what is
held, which is the same shape as the rule for `instance`. The second of those was not loose usage. A roadmap item titled
"Move ownership from a single holder to a set" and a last-holder promotion rule are about owners, and
read as though they are about the grant sense.

| Sense                                              | Became                                                   | Sites |
| -------------------------------------------------- | -------------------------------------------------------- | ----- |
| whoever a grant is recorded against                | **principal**, **group**, both named, or no agent at all | 17    |
| an owner                                           | **owner**                                                | 20    |
| whoever ends up with a token, and ordinary English | unchanged                                                | 5     |

Several of the first group read better with no agent: a role sets the ceiling, "the acts it permits"
rather than "the acts its holder could perform".

**Grant's definition was rewritten in the same pass**, since it opened with the retired word and
overlapped Permission on every other term. It now names what only a grant has: one decision, carrying
who made it, its period, and whether it was accepted, whose permissions expire and are revoked
together.

**A writing rule came out of it.** "A grant ending removes what its holder had" reads backwards: the
mechanism is the subject and the person is the object, so a reader holds two abstractions before
learning who it happened to. Recorded as put the person first and the mechanism after, with the tell
being a gerund or an event as grammatical subject with a person as its object. Scanning found one
more instance, in `permissions-model.md`, now fixed. The rule is explicitly not a ban on abstract
subjects: it applies where somebody is affected.

## Definitions shortened to one sentence each

The defining sentence says what the term is and stops; detail follows after a blank line. Applied to
Resource, Category, Principal, Capability, Permission, Role and Grant, and recorded as a rule.

Permission also lost its scope clause, which turned out to be the more accurate reading: the schema
keeps the scope on the grant row, `(user_id, category_id, resource_id, permissions, ...)`, so a
permission names the capability and the grant carrying it supplies the category and resource. The
detail below says so, since a permission is never held generally.

`entitlement` was dropped from Permission rather than replaced. Every candidate noun was worse:
_right_ carries moral freight, _clearance_ implies a process, _authority_ is already doing governance
work. Restructuring avoids the choice: **one capability a principal or a group may use, within one
category of one resource.**

Grant lost its inverted reading order and its details: **one decision to give permissions to a
principal or a group**, with who decided, the period, and the acceptance state moved below.

Capability had been closing twice, because the examples note was appended after a sentence that
already ended the entry.

The rule makes entries comparable, which is its second use: four words against six lines shows at a
glance where two run-on paragraphs do not.

## The entity list, reordered and reduced to one sentence each

    capability   Possible action a service offers.
    principal    Whoever asks to use a capability.
    group        Collection of principals.
    permission   Capability a principal or a group may use.
    role         Collection of permissions.
    grant        Action of assigning permissions to a principal or a group.
    resource     Collection of records, defined by an identifier they share.
    category     Collection of records, defined by properties they carry.

**The limits belong to the permission, not to the grant.** A capability is unbounded, since the
service can simply do it; a permission is that same action bounded on every side, and the bounding is
what makes it a different thing. The store keeps the limits on the grant because the permissions in
one grant share them, and reasoning from that table to the model had put them in the wrong place.

The order runs from what may be done to who may do it to what it is done to, so the data the model
governs is met last: nothing before it needs it, which the dependency rule then proves rather than

## Capability moved to zero

It depends on nothing and everything in the list depends on it, so it reads first and is numbered
zero, which marks it as the one term in the reading order that is not an entity.

Defined as **a possible action a service offers**. "Possible" earns its place: it separates what could

capability, since `grant.revoke` is offered by Usher's own admin API rather than by an application it

## The grants token is the Usher token, and its payload is permissions

The token's payload carried no grants. Every leaf was a capability name bounded by a resource and a

The token itself became the **Usher token**, 171 sites, with `(permissions token)` as the glossary

than by contents means the name makes no claim the payload has to keep up with, and it pairs against
`IdP token`, which is the contrast that matters in the flow.

**`access token` was considered and ruled out rather than weighed.** It is already the OAuth term for

## The field ambiguity is checked rather than trusted

It cost Arranger a painful migration, and Usher is currently clean: `fieldName`, `fieldValue`,
`nestedFieldNames`, and one bare `field` inside the glossary's own explanation of the distinction. So
this prevents drift rather than repairing damage, which is the dash check's profile: it sits at zero
and fires on regression.

Two patterns, both zero against the corpus today and both tested against synthetic defects:

- **An identifier ending in `field`.** Only `fieldName` and `fieldValue` are legitimate, since a bare
  one names neither the key nor the value and a reader has to guess which it holds.
- **A field being configured, stored, passed or sent.** Only a name can be, which is why
  configuration holds names.

The second needed widening after the first version missed "that field is per-catalogue plugin
configuration", the exact sentence found in the iMS integration doc, because modifiers sat between
the verb and the noun.

The tell is recorded as a table in `terminology-usage.md`: configuring, matching or identifying means
the name; cardinality, depth, values or which thing plays a role means the field.

## Fail-closed keeps the open tier, and the reason it is safe is mechanical

Revocation-uncertain mode suspended everything. It now suspends anything needing a granted
permission and keeps serving the open tier, because open access requires no grant: there is nothing
a revocation could withdraw and nothing for the bridge to be uncertain about. Withholding it hid data
that was never meant to be hidden, and a researcher reads missing rows as absent data rather than as
withheld data.

**Serving open during an outage needs no controller.** A plugin computes `open` by complement,
locally, from its own configuration rather than from the token, so the open slice is available
whether or not the controller is reachable. That was the fact the carve-out depended on, and it was
already recorded.

**It introduces no new exposure.** The known hazard of computing `open` by complement, an unmapped
category falling outside the set being subtracted and its records being served as open, is present
under normal operation too and is addressed by the startup check against Usher's category dictionary.
An outage neither creates it nor widens it.

**The exemption belongs to a bridge that started cleanly.** The startup check needs the controller,
so a bridge starting while the controller is unreachable has never validated its configuration and
cannot know what `open` excludes. It serves nothing until it has.

Propagated to `security-workflow.md`, `plugin-integration.md`, `architecture.md`, `glossary.md`,
`security-threat-model.md` and the onboarding page. `AGENTS.md` carries the old wording and is the
developer's to edit.

## API keys: four decisions, reached with the plugin's owner

Programmatic access runs on API keys from a Keycloak plugin the team maintains. Usher inherits them.
Recorded in `docs/atlas/roadmap/api-keys.md` with a roadmap entry and an index line.

- **Keys stay opaque, checked rather than self-verifying.** A signed credential with a multi-year
  expiry sits outside both halves of the revocation guarantee, and withdrawing one early needs the
  issuer-side state that self-verification removes. Familiarity points the same way and is the weaker
  argument. The check lands in the exchange path at session-start frequency, not per request.
- **The scope field carries Usher scope, intersected at exchange rather than validated at issue.**
  The field already exists and already holds EGO-style policy scopes, so two systems encode access
  today. Intersecting cannot add, which makes reduce-only structural rather than dependent on
  issue-time validation, keeps the dependency one-directional, and removes Usher's stake in an open
  question on the plugin side about which subject that validation runs against.
- **`DENY` is refused, not ignored.** Under intersection a negative is inert, and an inert
  restriction is a widening relative to what its author intended, which the additive-rendering
  decision exists to prevent. Refusing is loud and happens once; disregarding is quiet and happens
  every use.
- **The format waits on the capability vocabulary.** The parser splits on the last dot, so a dotted
  resource name survives and the separator rule was never the problem. The suffix must be a level,
  and EGO's READ and WRITE cannot express view without download, which is the axis narrowing exists
  for.

**Two constraints came from the plugin owner unprompted**, and both are the kind that are obvious in
code and invisible in a design document. The check authenticates its caller and requires a bearer
caller to own the key, so Usher needs basic auth and that is its first credential to Keycloak,
recorded in the threat model. And an unparseable scope makes the whole key unreadable rather than one
entry unrecognized, so the format is settled before the first key is issued in it.

**One claim of mine was withdrawn.** I said a key claiming more than its holder has is safe by
construction. That holds on Usher's path and nowhere else: Song and Score consume scopes directly and
intersect against nothing, so issue-time validation remains their only control until they move.

## Invitations gain audit events, and do not gain a grant state

An `invited` grant state was considered and rejected. It would either mean "before the person
registers", which makes a grant exist before a principal does and puts the `pending` collision back
under a new word, or "this grant arrived by invitation", which is provenance rather than state and is
already recoverable. Under acceptance it would be indistinguishable from `pending`.

The question pointed at a real hole elsewhere: the event catalogue had **no invitation events at
all**. So an invitation sent and never claimed vanished, taking with it whether someone was offered
access, who offered it, and whether a lapse was inaction or an address that reached nobody.

    invitation.creation   sent to an address with no account yet
    invitation.claim      an account confirmed it; the promised grants were created
    invitation.lapse      it expired unclaimed; the grants were never created

**The pair is split because a claim and a lapse are different facts.** Explicit refusal is already a
grant state, `declined`, so collapsing the ending into one event would record the loud refusal and
drop the quiet one. The claim event is also the only place the address and the principal appear
together, since invitations are keyed by email and grants by subject.

**One thing that looked like a defect and was not.** Three of thirteen act events listed `result` in
their fields while ten did not, which reads as the rule being broken. It is not: `result` is a
recurring property applying to acts, so restating it is redundant rather than required. Two
restatements removed; `auth.token.exchange` keeps its mention because it conditions other fields on
the value.

## Three corrections from an ARGO observation

A statement from another Overture context: a user is a data submitter for every study in their

**It confirms resource-scoped roles rather than challenging them.** Submitter-ness is per study, not

**A default is not a promise every service offers it.** `download` means nothing to a service serving

**Submitter is a role and not only provenance**, which corrects what was recorded yesterday. It is

## Catalogue carried four senses, and now carries one

STE says one word, one meaning, and the word had reached four. It keeps the sense it has in Arranger,
a body of data a service holds. Where it had come to mean a list of things, the replacement is the
plain word, because reaching for a longer one to say "list" is the habit these rules exist to stop.

| Sense                                                   | How it read                                      | Now                                      |
| ------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| the capabilities a service offers                       | `capabilities` is a catalogue rather than policy | the capability vocabulary                |
| the events Usher emits                                  | the full catalogue of auditable events           | a list                                   |
| Arranger's `catalogueId` container                      | bare, and sometimes qualified                    | Arranger catalogue, qualified every time |
| one schema, the scope a resource field name resolves in | bare, and sometimes qualified                    | catalogue, bare                          |

**The two data senses were contradicting each other inside one file.** `plugin-integration.md` said a
catalogue is Arranger's word with no equivalent concept in Usher's model, and a hundred lines later
said each body of data with its own store and schema is its own Usher catalogue. The glossary defines
the second. So bare now means Usher's unit, which is what these documents are about and what the
glossary entry already described, and Arranger's is qualified every time, since one `catalogueId` can
compose a second queryable type backed by an unrelated index and so hold more than one of them.

**The verb went with them.** `catalogued` meant listed, which is a third meaning rather than the
noun's meaning in a second grammatical role, so it falls under the adopted rule rather than the
part-of-speech rule that was tested and dropped.

**`vocabulary` keeps a narrower job.** It names a set of permissible names and nothing else: the
capability vocabulary an instance may extend, the event vocabulary fixing the `entity.act` shape.
That is a naming system rather than an enumeration, and no plain word carries it.

**The general rule this produced, and the boundary that makes it safe.** `terminology-usage.md` gains
"Reach for the plain word first", with the test written as a table: not word length, but whether the
longer word carries something the plain one drops. The rule stops at the glossary door. It governs
words chosen for how they sound and never words chosen for what they mean, so a defined term, an
industry standard or a settled keyword is held by one word, one meaning instead and stays put however
plain a near-synonym looks. Which rule applies is settled by asking whether the word is defined.

That boundary is written from a defect rather than anticipated. Applying plainness to the capability
sites as well as the event ones left `permissions-model.md` calling the object a list while
`rabac-alignment.md` called it the capability vocabulary, which is two words for one thing and breaks
the no-synonyms rule the same file adopts. The capability sites are back to `vocabulary`; the three
event sites and the verb stay plain.

**Checked rather than remembered.** `check-prose.sh` gains an eleventh pattern covering every retired
phrasing, in the wrap-aware block because each of them can break across a line. Tested against a
probe holding seven instances, two of them wrapped, and four legitimate uses: seven hits, nothing
false.

## DCAT becomes the outside check, and an overload list is opened

The terminology work had been testing words against each other inside one corpus, which is the
condition under which a group settles on a word that means something else everywhere else. W3C DCAT
defines several words already load-bearing here, so it becomes the outside reference: where it
defines a word Usher uses, its meaning governs. Recorded in `decisions.md`, with the class
definitions taken from the raw specification.

**The verification earned its keep immediately.** A summarizing fetch of the DCAT page rendered
`dcat:Dataset` as available "in one or more serializations or formats"; the specification says "in
one or more representations". Had the summary been quoted, a normative definition would have entered
this corpus altered.

**The hierarchy decides it, and reading the definitions without it misleads.** `dcat:Catalog` is a
sub-class of `dcat:Dataset`, which is a sub-class of `dcat:Resource`. Metadata about data and a body
of data are therefore not competing answers: a catalog is a dataset, and the extra word says more
rather than something else. A first reading here took them as a conflict and recorded that Arranger's
word was unsupported by the standard, which the hierarchy disproves.

**What an Arranger catalogue indexes is what settles it.** Largely metadata about sequencing files,
joined with clinical data about the donors those sequences came from, so it is a curated collection
of metadata about resources in the sense DCAT means. The platform being bio-research focused is what
makes that true rather than a coincidence: the records describe lab materials held elsewhere. The
clinical half is data rather than metadata about a `dcat:Resource`, and the sub-class relation
absorbs it, since whatever is not Catalog is still Dataset.

**The reading, since established against Arranger's code and published documents:** the queried API of Arranger, Lyric, Score and Song is
a `dcat:DataService`; one Arranger catalogue is a `dcat:Catalog` and so also a `dcat:Dataset`; the
records it indexes are a `dcat:Dataset`. The service and the catalogue were competing for one slot
only because they had not been separated.

**`ushered data service` becomes available as a third noun.** `data service` was on the books as a
role description, under a rule warning that a role becomes a synonym the moment it names the thing.
DCAT defining `dcat:DataService` is what lets it graduate: it now names a kind of thing rather than a
current job. It is the most precise of the three nouns, since an ushered application may be anything
and an ushered service serves requests of any kind, and it draws the plane boundary for free, because
Usher is a service and is not a data service. Recorded as available where the precision earns its
place rather than as a rename.

**The overload list is now tracked rather than recalled**, in `terminology-usage.md` under "Open
overloads, tracked": `dataset`, `artifact`, `payload`, `corpus`, `plane`, `scope`, ordered by damage
rather than by count, with `schema` surveyed and cleared. Two of those are worth naming here.
`artifact` carries a governance object and a published document under one word, and the governance
one is what enforcement fails open on. And the part-of-speech table keeps `scope` on the stated
evidence of five uses in the whole corpus, which is stale by an order of magnitude.

## A measurement defect that invalidated two published counts

`grep` on the interactive path is a shell function wrapping **ugrep**, and ugrep given `.` prints
`sub/a.md` where BSD `/usr/bin/grep` prints `./sub/a.md`. So `grep -v "^./.dev/sessions/"` is correct
against system grep and silently excludes nothing against the wrapper. Session files were counted in.
`ceiling` measured 46 and is 32; `plane` was recorded as 70 and is 87.

Two things follow. Anchor a path exclusion on a substring rather than on a leading `./`, and check the
file list rather than only the total, since a failed exclusion prints no error and returns a plausible
number. And `check-prose.sh` is unaffected, verified rather than assumed: its file list comes from
`git ls-files`, which emits repo-relative paths with no prefix, so its own exclusion does what it
says. This is the third measurement defect of the same family today, after `git ls-files` missing
five untracked files and a case-sensitive verification nearly recording a correct finding as
fabricated.

## Three smaller corrections

**The schema naming decision said "two rules" and lists three.** The third, that a set of tables split
by holder must name the holder on every one of them, governs a set rather than any single table, which
is presumably why it read as an addition. Heading and preamble corrected.

**The group-span question now records the reasoning that settles its direction.** A group landing
permissions across resources is the shape of a system administrator failing open: platform-wide reach
produced by a membership change that no resource's owner sees and that nobody is named as controlling.
Stated as a threat rather than a preference the answer is no, and what stays open is only how the
constraint is expressed in the schema.

**A citation pointed at a phrase that did not exist.** The onboarding audit cited "delegate the
reading, never the framing" as living in the delegation log, and it did not. The rule is real and is
the single rule behind every result in that log, so it was written in rather than removed from the
citation, along with the two corollaries it rests on: convergence ranks rather than filters, and the
verification is the weak link more often than the report.

## Still open after this pass

All three items this section listed at the start of the day were closed during it: the role
vocabularies, the four tables, and the owner-holds-viewer-access statements.

**Raised and not resolved:**

- **A grant has no id, and three audit events require one.** `grant.creation`, `grant.selfCreation`
  and `grant.revocation` all carry `grantId`, while `category_grants` is keyed by
  `(user_id, category_id, resource_id)` with no id column. Either that composite is the identity, in
  which case a holder may have at most one grant per category per resource and the audit field should
  be those three, or a grant has a surrogate id and the schema is missing it. An associative entity
  with a lifecycle is exactly where the distinction bites, since revocation, extension and expiry all
  have to name one row.
- **The Usher scope format**, waiting on the capability vocabulary, which waits on implementation.
- **Usher's basic-auth credential to Keycloak**: whether it is its own client, and how it rotates.
- **Event types carry no reverse-DNS prefix** where CloudEvents says they SHOULD, and the spec's
  reason is the multi-service correlation this design wants.
- **Which permissions each shipped role carries by default**, which is seeding rather than modelling.
- **Submission-path items from the embargo thread**: resource creation as a precondition, and no
  automatic categorization.
- **The profile view's four open questions**, in `design/profile-view.md`.
- **What RABAC defines for assignment.** The paper has not been read. It matters because the ceiling
  and grant structure is taken from it deliberately, and because a proposal to collapse the two
  stages was made and withdrawn today on exactly that ground: collapsing them multiplies roles, and
  not multiplying roles is what RABAC is for. This is the next thing to do.
- **Whether a role's ceiling is global to the principal or held per resource.** The corpus says per
  resource once, in a glossary aside. It blocks the `ceiling` definition as well as the calculation.
- **What acceptance is for**, since a group grant carries no state and is live the moment it exists,
  which means adding someone to a group skips the step that granting them the same thing by name
  would require.
- **Two cases in the token calculation**: whether an authenticated principal with no grants is
  distinguishable from an anonymous visitor with no grants, and what a grant naming a category its
  resource no longer carries should do.
- **Glossary entries for `ceiling` and `plane`.** Both are one-meaning terms with no definition
  anywhere, which the term-of-art rule forbids; `ceiling` waits on the question above, `plane` does
  not and can be written now.
- **A reply is owed upstream** on the register measurement. The finding is recorded here and the
  people who produced it have not heard back, which is the failure mode where an unsent message is
  indistinguishable from an ignored one.
